# Architecture

## Core Concepts

App, Agent, Trigger, Run, Step, State, Tool, Workspace, Notifier, Store. Keep the concept surface at about ten. chamvi never wraps the AI SDK: models (`LanguageModel`), messages (`ModelMessage`) and tool sets (`ToolSet`) are passed through as-is.

`@chamvi/core` (as built in plan 001) holds: agent and trigger definitions, the `Engine`, step checkpoints, budgets, effect tools, approvals with signed resume tokens, recovery and drain, agent state, streaming deltas, structured output, run artifacts (attachments and tool files), the `IStore`/`INotifier` interfaces, `MemoryStore`, `consoleNotifier()`. Everything time-based goes through an injectable `IClock` (`systemClock`; `ControllableClock` in tests). The public surface is `src/index.ts`. `@chamvi/test-kit` exports `describeStoreContract` and `ControllableClock`.

## Engine

`new Engine({ store, agents, resumeSecret, ... })` validates at construction (`InvalidAgentDefinitionError`): `resumeSecret` must be non-empty, agent names unique, every `notify` must name a key of `notifiers`. Defaults: `claimTtlMs` 60 s, `maxConcurrentRuns` 4, `owner` `${hostname}-${pid}`, `clock` `systemClock`, `onError` logs to `console.error`. `start()` recovers and begins polling; `dispatch`, `cancel`, `resume`, `tick`, `recover` and `drain` are the operations; `provide(key, value)` (`IContextProvider`) holds the values tools inject (see [Context](#context)). The engine is the one source of what an app is built from: `store` and `clock` are public readonly fields, `getAgent(name)` and `listAgents()` (registration order, a new array) read the registered agents, so `@chamvi/scheduler` and `@chamvi/http` take only the engine. `on(type, listener)` is typed per event (`run.updated` carries `run`, `step.appended` carries `step`, `run.delta` carries `delta`) and sees local events only.

**Live registry** (`engine/registry/`, plan 025a): the agent set changes at runtime. `putAgent(agent, { revision? })` registers an agent or replaces the one of the same name in place (a new one goes last), refusing an unknown `notify` like the constructor (`assertRegistrable`), and resolves `added | replaced | unchanged` (`unchanged`, no event, for the same object at the same revision); `removeAgent(name)` resolves whether it was registered here; `agentRevision(name)` is the revision an agent was registered at (`undefined` for a code agent). Both emit `agents.changed` (`AgentChange { name, kind: 'added' | 'replaced' | 'removed' }`, local; `EngineEvent = RunEvent | AgentChange`). Every marker operation runs under the store lock `agents:<name>` (`withAgentLock`, owner a fresh `randomUUID()` per attempt, TTL `AGENT_LOCK_TTL_MS` 300 s, retried every `claimTtlMs / 3` on the `IClock`, `InvalidRunStateError` after 300 s): with a `revision` (a folder's content hash), `syncRevision` reads the marker and, when it differs, cancels the agent's unsettled runs (`queued | running | waiting | interrupted`) created before `changedAt = now` (only when a marker existed: a first sight cancels nothing), then writes `{ agent, hash, changedAt }` (`changedAt` taken right before the write) and sweeps again for runs created before it (a replica at the old hash may create and start one until the write lands), so a change cancels once across replicas; while it syncs, this engine starts no run of the agent (`syncing`, checked by `prepareStart` and `isCurrent`); without one, replacing a registered agent cancels its unsettled runs created before now. `removeAgent` first unregisters the agent and emits `removed` (no further dispatch here), then `dropRevision` cancels all unsettled runs and deletes the marker when one exists (also for an agent this engine never loaded), unless this engine had the agent at another revision (a newer one registered elsewhere: marker and runs left alone); without a marker it cancels the runs of an agent registered here (code or folder: no replica runs it any more, so a lagging replica's runs never stay queued). Cancels run concurrently through `engine.cancel` (a run settled or gone meanwhile is skipped, other failures go to `onError`). `dispatch` for an agent the engine does not hold throws `AgentNotFoundError` (`agent_not_found`, http 404).

## Agents

`defineAgent({...})` takes a typed config object and returns `{ name, definition }` with the budget defaults applied (`maxSteps: 20`, `timeoutMs: 15 min`). Agent names match `^[a-z0-9]+(-[a-z0-9]+)*$`, at most 64 chars, unique per app; trigger ids must be unique per agent (`InvalidAgentDefinitionError` otherwise). `tools` is a plain `ToolSet` or a factory `(ctx: ToolContext) => ToolSet`, called per execution. `assembleTools` builds one `ToolContext { run, state, artifacts }` per execution (shared by the factory and every call) and passes it as the `ToolLoopAgent`'s `toolsContext` (`as never`: a `ToolSet` infers no context type) only to tools whose `contextSchema === toolContextSchema` (`tool/`: `defineTool()`, `defineEffectTool()` and the state tools set it; `validate` returns the value by identity and rejects a non-object, which fails the run, since the AI SDK validates the context outside its tool-error handling). The agent's `toolsContext?: Record<string, unknown>` entries go unchanged (by reference, never cloned or stored) to tools that are not chamvi's (also to one without a `contextSchema`); an entry naming a chamvi tool or no tool is an `InvalidAgentDefinitionError` (`assertToolsContext`, `agent/helpers.ts`: thrown by `defineAgent` for a plain set, a failed run before any model call for a factory), and a third-party tool with a required `contextSchema` and no entry (or a rejected one) fails the run. `toRunError` turns that AI SDK `TypeValidationError` (`context.field === 'tool context'`) into a `ValidationError` naming the tool and the issue paths only, since the SDK's message (and some validators' issue messages) hold the entry's value, which may be a secret; chamvi's own missing-context issue keeps its message. `StepResult.toolsContext` is never stored (steps are built field by field). `artifacts` (`IRunArtifacts`: `put`, `get`, `list`) is scoped to the run (`get` of another run's artifact is `undefined`) and is no effect by itself (wrap `put` in `defineEffectTool` for exactly once). `output` takes an AI SDK `Output` (`Output.object({ schema })`), passed to `ToolLoopAgent` as is. `approvals` maps tool names to `'user'` or a policy function (`'user' | 'allow' | 'deny'`), translated to the AI SDK's `toolApproval`. `notify` names a notifier registered on the engine (checked in the `Engine` constructor). `toolPolicy(toolName, { run })` is applied to the merged tool set (state tools included) in `assembleTools`: the allowed names become the `ToolLoopAgent`'s `activeTools`, so a refused tool is never offered to the model, while every tool stays in `tools` so an approved call from an older history (policy tightened before the resume) still executes through `wrapToolsForRun`, which re-checks every call and answers a refused one with a `ToolNotAllowedError` tool error (the run goes on). A model that calls a refused tool anyway gets the AI SDK's `NoSuchToolError` answer (the tool is not in `activeTools`); `refusedCallError()` (`execute/helpers.ts`) records that tool step as `ToolNotAllowedError` (`tool_not_allowed`), only for a tool of the full set whose invalid call carries a `NoSuchToolError`, so a genuinely unknown tool keeps the SDK's error. The policy should depend only on the run snapshot, so the tool set is stable across executions. `requireToolPermission({ withoutInvoker? })` (`permission/`) offers a tool when the invoker holds `tool:<agent>:<tool>` (`hasPermission`: `*` alone grants everything, a `*` segment matches one segment, segment counts must match; `@chamvi/http` delegates to it); runs without an invoker follow `withoutInvoker` (default `'deny'`).

### Context

`context/` (core): `defineContextKey<T>(name)` returns a frozen `ContextKey<T>`, unique per call (registered in a module-private `WeakSet`; the name is for messages only, an empty or non-string one is `InvalidAgentDefinitionError`). `engine.provide(key, value)` stores the value by reference in the engine's `Map` and refuses a foreign key, also one of another `@chamvi/core` copy a package resolved (`Context "<name>" has no key from defineContextKey() of the engine's @chamvi/core: ...`), `undefined` (`Context "<name>" needs a value.`) and a second value for one key (`Context "<name>" is already provided.`), each `InvalidAgentDefinitionError`; a value provided after `start()` reaches the next execution, since the map is read at call time. There is no `EngineOptions.context`. The engine passes the map as `ExecuteContext.provided`; `assembleTools` binds it to the execution's `ToolContext` through a module-private `WeakMap` (`bindProvided`, `context/helpers.ts`) right after building the context and **before** the tools factory runs, so `inject(ctx, key)` / `tryInject(ctx, key)` return the same object in the factory, in `execute` and in the effect hooks (`alreadyApplied`, `effectKey`). `ToolContext` stays exactly `{ run, state, artifacts }` (no own key, string or symbol), and nothing provided is stored, cloned or serialized into steps, checkpoints or runs. A spread copy (`{ ...ctx }`) or a hand-built context has no binding: `inject` takes the context the engine passed. `inject` without a value throws `ContextNotProvidedError` (`context_not_provided`, naming the key only, never a value): a tool error in `execute` and in the effect hooks (they run inside the wrapped `execute` of `wrapToolsForRun`), a run failure before any model call in the factory (`assembleTools` rethrows it, `guardedExecute` settles the run `failed` and reports it to `onError`). Feature packages export a core-only pair per shared instance (`provide*Context(engine, value)`, `inject*Context(ctx)`) and keep the key internal.

## Triggers and the Envelope

`cron()`, `http()` and `webhook()` build `TriggerDefinition`s (`{ source, id, options, concurrencyKey?, idempotencyKey? }`). `http({ schema? })` is the control-plane trigger (id `http`, so at most one per agent): REST `POST /agents/:name/runs`, the UI and MCP `run_<agent>` start runs through it (envelope `trigger: 'http'`, `source: 'http'` or `'mcp'`). `webhook({ path, schema?, idempotencyKey?, concurrencyKey? })` is a generic webhook (id `webhook:<path>`, many per agent, `path` must start with `/`, envelope `source: 'webhook'`); the key functions are copied onto the definition only when given. `cron()` validates the expression with cron-parser and stores the overlap policy (default `skip`; others `queue-one`, `allow`), enforced by `@chamvi/scheduler` (see [Scheduler](#scheduler)). Firing cron and HTTP triggers is not part of core: `engine.dispatch(envelope)` is the only intake; `@chamvi/scheduler` fires `cron()`, `@chamvi/http` serves `http()` and `webhook()` (see [HTTP](#http)), `@chamvi/github` its `githubWebhook()` triggers (see [GitHub](#github)).

```ts
interface TriggerEnvelope {
    id: string;              // defaults to a UUID
    agent: string;
    trigger: string;         // trigger id, e.g. 'http'
    source: 'cron' | 'http' | 'webhook' | 'github' | 'mcp';
    payload: unknown;
    idempotencyKey?: string;
    concurrencyKey?: string;
    thread?: string;
    invoker?: Invoker;       // { id, kind, name?, permissions }, from an authenticator only
    receivedAt: Date;        // defaults to now
}
```

`dispatch` validates a given invoker (non-empty `id` and `kind`, `permissions` an array of strings, `ValidationError` before any write) and stores a copy of only those fields. It is a snapshot (identity and grants, never a token): a run paused on an approval keeps it, and revoking a grant does not reach a run that holds it. The idempotency scope includes the invoker (see Intake), so a deduplicated dispatch always comes from the invoker of the run it returns. Tool code reads it as `context.run.trigger.invoker` (tools and the factory's `run`), `ctx.run.trigger.invoker` (effect hooks) and `runtimeContext.trigger.invoker` (approval policies).

The envelope (source, trigger, payload) is rendered as a JSON block and becomes the run's first user message: string content, or with attachments `[{ type: 'text', text }, ...one file part per attachment]` whose `data` is the marker `chamvi-artifact:<id>` (`ARTIFACT_URI_PREFIX`, internal). `TriggerEnvelope.attachments?: Artifact[]` holds their metadata; `DispatchEnvelope.attachments?: ArtifactInput[]` takes the bytes.

## Run Lifecycle

Run statuses are exactly `queued | running | waiting | completed | failed | cancelled | interrupted`. Steps are `llm | tool | wait`.

```
dispatch -> queued -> running -> completed | failed | cancelled
running -> waiting (approval) -> queued (resume or timeout answers it) -> running
running -> interrupted (drain) -> queued (recover) -> running
running with an expired claim (crash) -> queued (recover) -> running
```

- **Intake**: `dispatch` first refuses an `idempotencyKey`, `concurrencyKey` or `thread` above `TRIGGER_KEY_MAX_LENGTH` (255, the store's varchar width) or with a NUL (`assertTriggerKey()`, `trigger/key.ts`, `ValidationError`, before any store write); intakes (`@chamvi/http` hooks, `@chamvi/github`) use the same helper. With an `idempotencyKey`, `dispatch` claims `(scope, key)` in the `IIdempotencyStore` (TTL 7 days); the scope is `<agent>:<source>`, and with an invoker `<agent>:<source>:<kind>:<id>` with `kind` and `id` each `encodeURIComponent`-ed (`idempotencyScope()`, `trigger/helpers.ts`), so two invokers sending the same key get a run each and one principal cannot squat another's key; a duplicate returns the existing run id with `deduplicated: true`. A key whose run was never created (createRun failed after the claim) is healed by the next dispatch, which creates the run under the reserved id; `createRun` is insert-if-absent, so concurrent healers create it once.
- **Attachments**: `dispatch` validates each `ArtifactInput` (`mediaType` `type/subtype` without parameters, optional string `filename`, `data` a `Uint8Array`; `ValidationError`) before any store write, then, after the idempotency dedupe returned (a duplicate stores nothing), stores each as an artifact of the run (id `<runId>.<index>` from `attachmentIds()` in `artifact/module.ts`, the index zero-padded to one width per dispatch, at least 4 digits, so `listArtifacts` (createdAt, then id) returns the input order; `size` = byte length, `createdAt` = run createdAt) and creates the run. Tool artifacts (`artifacts.put()`) keep `randomUUID()` ids. `storeArtifact` relies on `putArtifact`'s insert-if-absent: when the id is taken by the same run it returns the stored artifact (another run's: `InvalidRunStateError`), so concurrent healers of one reserved key write to the same ids, the second write is a no-op and `trigger.attachments` always names what the store holds (the first writer's bytes). A crash between storing and `createRun` leaves orphan artifacts (accepted; nothing purges artifacts yet), and a racing healer that sends more attachments than the winner leaves its extra indexes listed on the run.
- **Scheduling** (`engine/queue.ts`): a pass lists `queued` runs FIFO (createdAt, then id) and starts them up to `maxConcurrentRuns`. **Execution guard**: a pass that found queued runs first builds a start predicate (`prepareStart`, one `listAgentRevisions()` read, skipped while no folder agent is registered): a run may start when `cancelRequested` (it settles `cancelled`), or when its agent is registered here and is a code agent or loaded at the stored marker's hash; any other run is skipped before any claim and stays `queued` for a replica that has the agent's current revision (never failed with `unknown agent`). `execute()` re-checks after the claim (`isCurrent`, one `getAgentRevision`) and hands a run whose agent was removed or replaced meanwhile back to `queued` (owner-guarded); recovery requeues as before, so the guard also covers recovered runs; `tick()` keeps skipping notifications of unknown agents. A keyed run starts only when no other run of the same agent and `concurrencyKey` is `running`, `waiting` or `interrupted`; check, claim and transition happen under a store lock `concurrency:<agent>:<key>` so it holds across replicas.
- **Claims**: `claimRun(id, owner, claimTtlMs)` is a lease, renewed every `claimTtlMs / 3`. The poll runs on the same interval and calls `tick()` (approval expiry) and `recover()`. Every write of a running run is conditional on status and owner; an engine that loses its lease aborts the execution, writes nothing more and reports a `LeaseLostError` to `onError`.
- **Execution** (`engine/execute.ts`): one `ToolLoopAgent.stream()` call per execution (consumed to the end; settling reads the result's `steps`, `finishReason`, `text`, `output` promises), starting from the latest checkpoint. Checkpoints hold the stored messages (artifact markers); the model gets a hydrated copy whose marked file parts carry the bytes from `readArtifact` (a missing one fails the run with `ArtifactNotFoundError`), and the engine saves `[...storedInitial, ...responseMessages]`, so the approval resume path works on stored messages. Each `text-delta`/`reasoning-delta` part is emitted as `run.delta` (`RunDelta { runId, step, kind: 'text' | 'reasoning', text }`, `step` = the checkpoint `stepIndex` the step is saved under); deltas are never stored, local to the executing replica and never emitted once the execution was abandoned. No opt-out: every AI SDK provider streams. A model call that fails mid-stream (an `error` part) still ends its step: the AI SDK finishes it with finish reason `error`, so the engine appends the `llm` step (the partial text) and saves its checkpoint before the run fails with that error (unlike the former `generate()`, which wrote nothing; pinned in `stream.spec.ts`). A step whose provider stream closed without its finish part (the AI SDK then synthesizes finish reason `other` and never executes the step's tool calls) fails the run with `IncompleteResponseError` (`incomplete_response`); the engine tells it apart through `onLanguageModelCallEnd`, which fires only for a received finish, so a provider that reports `other` itself still completes.
- **Structured output**: with `output`, a `completed` run's `output` is the parsed value (else the text); a final answer that fails to parse or validate (`NoOutputGeneratedError` or a schema failure) fails the run with `ValidationError` (`validation_error`, message from the cause, the cause cut to `MAX_ERROR_CAUSE_LENGTH` 500 characters plus an ellipsis, `execute/constants.ts`). Before parsing, a loop end with no answer fails with `IncompleteResponseError` (`incomplete_response`, `incompleteOutput()` in `execute/helpers.ts`): finish reason `length` (cut answer) or `tool-calls` outside a budget stop (a call nothing executed, e.g. a tool without `execute`, named in the message). A plain agent keeps completing with the text in both cases (decided: its text is still usable and the llm step records the finish reason). The "step limit reached by an earlier execution" branch parses the checkpoint's last assistant text through `output.parseCompleteOutput` with the same rules (a `length` checkpoint is incomplete). The `ToolLoopAgent` gets `withoutPartialOutput(output)` (`execute/helpers.ts`): a prototype copy whose `parsePartialOutput` returns `{ partial: text }` without parsing, so the AI SDK neither re-parses the accumulated answer per delta nor holds deltas back (returning `undefined` would publish the whole text at `text-end` only); `parseCompleteOutput` and `responseFormat` stay the agent's. After every step the engine appends the steps and saves a checkpoint (messages plus the step's `finishReason`). A cancel or drain abort lets the step-end writes in flight finish (all tool rows and the checkpoint of a completed step), so a recovery does not redo a step whose tools already ran; an abandon guard then stops a still-running generate from writing after the run settled. Each execution owns an `AbortController` combined into the signal the agent and the tools get (`run.signal`); it aborts on every exit, so a throw while consuming the stream (e.g. a throwing `onError` behind a failing `run.delta` listener) cancels the model stream instead of leaving it open.
- **Budgets** (`engine/budget.ts`): `maxSteps` and `maxTokens` are stop conditions, `timeoutMs` an abort signal per execution (built on the `IClock`). Stopped by a budget while the last step asked for tool calls: `failed` with `BudgetExceeded`; otherwise `completed` (a plain agent), or for an agent with `output` the structured-output rules apply (a `length` finish fails with `incomplete_response`). Timeout: `failed` with `Timeout`.
- **Tool errors** go back to the model as tool-error results; only `FatalToolError` (and infrastructure or store failures) fail the run.
- **Cancel**: aborts a local execution (`cancelled`), or marks a `queued`/`waiting` run cancelled. A run `running` on another replica (or `interrupted`) gets `cancelRequested: true`; the owner sees it in `recover()` on its next poll and aborts with stop `cancel`, and an execution that starts on such a run settles it `cancelled` without a model call. A cancel that races a pause (the abort cannot interrupt the `waiting` write) cancels the run the pause left waiting, without notifying.
- **Drain**: `drain({ timeoutMs })` stops polling and starting runs, waits for in-flight runs (default 30 s), then aborts the rest and marks them `interrupted` with the claim released. `stop()` only stops polling.
- **Recovery**: `recover()` (on `start()` and every poll) claims each `running` or `interrupted` run whose claim expired or was released and requeues it; the next execution continues from the latest checkpoint. A step whose checkpoint never landed runs again.

## Approvals

- A tool call needing approval ends the step; the first unanswered `tool-approval-request` becomes the run's `WaitPoint` (`approvalId`, `toolName`, `input`, `expiresAt`, `tokenId`). Other approval requests from the same step are dropped from the history; the model asks again after the resume (one approval per pause).
- `running -> waiting` releases claim and slot (a keyed run keeps its key blocked). The notifier named by the agent gets one `approval` notification per wait point, carrying its `approvalId` and a resume token, with `NotifyOptions { idempotencyKey, trigger }` (`trigger` = the run's stored envelope, so a transport finds the run's issue without a store); a successful send records `waiting.notifiedAt`. `tick()` re-sends on every poll while `notifiedAt` is missing (a failed send, or a crash mid-send); a store lock `notify:<run>:<approval>` held for one attempt (at most `claimTtlMs`) keeps replicas from sending concurrently, and the notifier's `idempotencyKey` (`<run>:<approval>`) dedupes a send whose record was lost.
- Resume token: `base64url(JSON { runId, approvalId, tokenId, exp }) + '.' + base64url(HMAC-SHA256(resumeSecret, payload))`, compared in constant time.
- `resume(token, decision)` validates an optional `decision.approver` (an `Invoker`, recorded as `output.approver` on the `wait` step), verifies the token against the current wait point, moves `waiting -> queued` (guarded by `expectStatus`, so only one answer writes), appends the `tool-approval-response` to the checkpoint and a `wait` step, then clears `waiting`. A failure undoes back to `waiting`, so the token stays valid; a crash in between re-pauses on the same wait point.
- `approve(runId, { approvalId, approved, reason?, approver? })` (`ApprovalAnswer`) answers the current wait point without a token: it validates the approver before any store read, then refuses a run that is not waiting, another `approvalId` or a wait point at or past `expiresAt` (`tick()` denies that one) with `InvalidRunStateError`, and goes through the same `answer()` path, whose `stale` factory makes a run that moved on to another approval meanwhile `InvalidRunStateError` here and `InvalidResumeTokenError` for `resume()`/`tick()`; the token notified earlier is spent by the same transition.
- `inspectResumeToken(token)` checks a token's signature (constant time) and expiry and returns its claims (`runId`, `approvalId`, `tokenId`) without touching the store (`InvalidResumeTokenError` otherwise), so an intake layer can authorize against the run's agent before `resume()`; `resume()` still checks the token against the current wait point.
- `tick()` also denies approvals past `expiresAt` with reason `approval timed out` (default `approvalTimeoutMs` 24 h). A resumed approval gets one step beyond `maxSteps`, so an approval on the last step is still answered.

## Store Contract

The store is a set of small interfaces combined as `IStore` (`src/store/types.ts`):

| Interface | Holds |
|-----------|-------|
| `IRunStore` | Runs; `updateRun` with `expectStatus`/`expectOwner` guards; `listRuns` ordered by createdAt then id (both ascending, or both descending with `order: 'desc'`), unbounded without `limit`; `claimRun`/`renewClaim` leases |
| `IStepStore` | Append-only steps per run |
| `ICheckpointStore` | Latest checkpoint per run (highest `stepIndex`; equal index replaces) |
| `IIdempotencyStore` | `claimKey(scope, key, runId, ttl)`: first caller wins |
| `ILockStore` | `acquire`/`release` of keyed leases |
| `IEffectStore` | Recorded effect results by effect key |
| `IStateStore` | Per-agent KV (`kvSet(..., undefined)` removes the key; `kvList(agent, { limit?, offset? })` in key code-point order, unbounded without `limit`) and document collections (`where` = top-level equality) |
| `IAgentRevisionStore` | One revision marker per folder agent, `AgentRevision { agent, hash, changedAt }` (no code): `getAgentRevision`, `setAgentRevision` (upsert), `deleteAgentRevision` (missing is a no-op), `listAgentRevisions` (agent code-point order); copied in and out |
| `IArtifactStore` | `putArtifact(artifact, data)` (atomic insert-if-absent, `false` keeps the stored one), `getArtifact` (metadata), `readArtifact` (bytes, a plain `Uint8Array`), `listArtifacts(runId)` (createdAt, then id); bytes copied in and out |

Rules every implementation must keep: a TTL created at T with `ttlMs` is expired at exactly `T + ttlMs`; values are copied in and out (no aliasing); atomic operations are atomic across callers. `MemoryStore` implements it in-process (structured clones, no await between check and write). `describeStoreContract((clock) => store)` from `@chamvi/test-kit` is the shared Vitest suite every store must pass; the factory must use the given `ControllableClock` for expiry. Redis is never required.

`TypeormStore` (`@chamvi/store-typeorm`) is the TypeORM store (PostgreSQL only). Every method goes through the entities' repositories and query builders; the only hand-written SQL is the `jsonb_exists` key check in `docList` (TypeORM has no key-existence operator), containment uses `JsonContains`; `store/helpers.ts` maps entities to `Run`, `Step` and `Checkpoint` (a `RETURNING` row is hydrated through the entity metadata). Every atomic operation is one statement: `insert().orIgnore()` returning `id` (`createRun`, `putArtifact`), `insert().orUpdate()` with the overwrite condition `expires_at <= now` returning a row (`claimKey`, `acquire`), a conditional `update()` (`claimRun`, `renewClaim`, the `updateRun` guards, the latter returning `*`) and `insert().orUpdate()` with the overwrite condition `step_index <=` (`saveCheckpoint`). Time comes from the `IClock` as a parameter, never the database's `now()`. Values are `jsonb` through column transformers (`entities/constants.ts`): the Postgres driver writes `JSON.stringify` and turns `null` into SQL `NULL`, so the transformers hand it a `toJSON` wrapper carrying the sanitized value (NUL and lone surrogates become U+FFFD); `JSON_VALUE_TRANSFORMER` (state, docs, effects, checkpoint messages) keeps `null` as JSON `null`, `OPTIONAL_JSON_TRANSFORMER` (run and step columns) stores it as SQL `NULL`. `trigger.receivedAt`, `trigger.attachments[].createdAt`, `waiting.expiresAt` and `waiting.notifiedAt` are revived as `Date`. Only the latest checkpoint is kept. Artifacts live in `chamvi_artifacts` (`ArtifactEntity`: `id` varchar(128) PK, `run_id` indexed, `agent`, `media_type`, `filename` nullable, `size` int, `data` `bytea` with `select: false`, `created_at` timestamptz; migration `1792368000000-artifacts.ts`); `chamvi_idempotency_keys.scope` is varchar(1024) (migration `1792454400000-idempotency-scope.ts`, a hand-written `ALTER COLUMN ... TYPE`, since TypeORM's generated length change drops and re-adds the column); `chamvi_kv.key` is `COLLATE "C"` (migration `1792540800000-kv-key-collation.ts`, `KvKeyCollation1792540800000`, hand-written the same way), so `kvList` orders by code point; markers live in `chamvi_agent_revisions` (`AgentRevisionEntity`: `agent` varchar(64) `COLLATE "C"` PK, `hash` varchar(128), `changed_at` timestamptz; migration `1792627200000-agent-revisions.ts`, `AgentRevisions1792627200000`), `setAgentRevision` a repository `upsert` on `agent` (no compare needed: the engine holds `agents:<name>`), `listAgentRevisions` ordered by `agent`; `getArtifact`/`listArtifacts` never load `data`, `readArtifact` returns a plain `Uint8Array`. `migrateStore(dataSource)` runs the migrations under the advisory lock `chamvi:migrations`; `purgeExpired(now?)` deletes expired idempotency keys and locks (nothing calls it automatically yet). Documented divergences from `MemoryStore`: opaque JSON loses `Date`/`undefined`/`Map` fidelity, `null` in an optional run or step property reads back absent, `putEffect(key, undefined)` reads `{ result: null }`, `docUpsert(..., undefined)` reads `doc: null`, `docList` `where` is `jsonb` containment and orders by `id`, `listRuns` ties use `COLLATE "C"`.

## Idempotency and Side Effects

1. Trigger dedupe at intake via `IIdempotencyStore`.
2. Completed steps are never repeated: execution resumes from the latest checkpoint.
3. Side-effecting tools use `defineEffectTool()`. Per call the wrapper (`wrapToolsForRun`) returns the recorded result for the effect key, else asks `alreadyApplied(effectKey, input, ctx)`, else executes and records the result; both hooks get the `ToolContext` (`ctx.run`, `ctx.state`, `ctx.artifacts`), and a custom `effectKey(input, ctx, options)` also gets the AI SDK call options (`toolCallId`, `messages`, e.g. to key by model step). The default key is `${ctx.run.runId}:${toolName}:${sha256(canonical JSON of input)}`. A throwing execute records nothing; a crash between the effect and the record repeats it unless `alreadyApplied` finds it (`effectMarker(key)` is the hidden marker to embed). Parallel identical calls in one step share one application.

## Agent State

`createAgentState(agent, schema, store)`: KV (`state.get/set`) plus typed collections declared as `state: Record<name, StandardSchemaV1>` in `defineAgent`. `upsert` validates with the collection's Standard Schema, mapped through `@validup/standard-schema` (`ValidationError` with the validup `issues` on failure, nothing stored). With a schema, the model also gets `state_<coll>_list`, `state_<coll>_upsert` and `state_<coll>_remove` tools (`createStateTools(schema)`; chamvi tools reading `context.state`, upsert and remove are effect tools); user tools win on a name clash.

## Scheduler

`@chamvi/scheduler` fires `cron()` triggers; it depends on `hubwire` (croner inside) and is a peer of core.

- `createScheduler({ engine, agents?, owner?, lockTtlMs?, onError? })` builds one hubwire `defineScheduledComponent` per cron trigger of `engine.listAgents()` (or of the agents named in `agents`, resolved by `selectAgents()` in `scheduler/helpers.ts`: a name the engine lacks or given twice is `InvalidAgentDefinitionError`), named `cron:<agent>:<triggerId>`, with `lock: createStoreScheduleLock(engine.store, owner)` (`ILockStore.acquire`, never released) and `lockTtlMs` default `SCHEDULE_LOCK_TTL_MS` (10 min). hubwire's tick key is `${name}:${scheduledAt ISO}`. Every hubwire definition error (expression croner rejects, timezone, `lockTtlMs`) throws `InvalidAgentDefinitionError` from `createScheduler`, before `start()`.
- Live components: the scheduler keeps its components per agent (`buildAgentComponents()`, `scheduler/helpers.ts`) and follows `agents.changed` (only for the names in `agents` when given, so agents registered later are not scheduled there): `added` builds and (once started) starts the agent's components, `replaced` stops the old ones and builds the new, `removed` stops them. A replacement hubwire refuses goes to `onError` and leaves the agent unscheduled (never a throw). Retired components stop in the background; `stop()` unsubscribes, stops every component and awaits their `settled()` plus the retired ones; `start()` is a no-op after `stop()`.
- `runOnStart: false` always: a start pass never takes hubwire's lock and would fire on every replica. hubwire skips a locked tick fired `lockTtlMs` or more late; `onSkip` is not wired (N - 1 replicas skip every tick). Lock, overlap and dispatch failures reach `onError(error, { agent, trigger })`.
- `fireCronTrigger({ engine, agent, trigger, scheduledAt })` is one tick: overlap check (over `engine.store`), then `dispatch` with source `cron`, payload `options.payload ?? { scheduledAt: ISO }`, idempotency key `<triggerId>@<scheduledAt ISO>` (the trigger's own `idempotencyKey()` is ignored), `concurrencyKey = trigger.concurrencyKey?.(payload) ?? (overlap === 'allow' ? undefined : trigger.id)`.
- Overlap: active runs are `queued | running | waiting | interrupted` of the agent filtered by `run.trigger.trigger`. `skip` skips while any is active, `queue-one` while one is `queued`, `allow` never. The check-then-dispatch race is made harmless by the default concurrency key (the extra run waits).
- Shutdown order: `await scheduler.stop()` (stop, then `settled()` per component), then `await engine.drain()`.
- `runJob({ engine, agent, trigger?, pollMs?, drainTimeoutMs?, signal? })` fires once at `engine.clock.now()`, then always starts the engine and calls `engine.tick()` once (so a skipped tick still recovers leftovers of earlier jobs and times out expired approvals), waits via `run.updated` plus an `engine.getRun` poll (`pollMs`, default 1 s, covers another replica) for `completed | failed | cancelled | waiting`, or for `queued` behind a `waiting` run of the same concurrency key (`queue-one` behind an approval), then `drain({ timeoutMs })` (default 30 s). Exit code 1 for `failed`/`cancelled`, else 0; an overlap skip returns `skipped` after the drain. It starts a full engine over the shared store (every queued run of every agent), so size the drain timeout. `signal` (additive, for the CLI's SIGTERM): already aborted when called, it fires nothing and starts nothing (`skipped`); aborted during the dispatch, the engine never starts and the stored run answers (`queued`, exit 0); checked again after `engine.start()`, so a stop that arrived meanwhile skips the approval tick; aborted while waiting, the wait ends and the drain runs, answering the run as the drain left it (`interrupted`, exit 0).

## GitHub

`@chamvi/github` connects a GitHub App; it depends on `@octokit/core` with `plugin-paginate-rest` and imports only types from `@chamvi/http` (nx stays acyclic: github -> http -> core).

- `createGithubApp({ appId, privateKey, webhookSecret, installationId?, slug?, baseUrl?, clock?, fetch? })` validates eagerly (`InvalidAgentDefinitionError`: empty `appId`, a key that is no RSA private key, empty secrets, an `installationId` that is no positive integer, a non-empty `baseUrl` that is no absolute https URL without query or hash (`normalizeBaseUrl`; empty is the default API), a `slug` that is not `^[a-z0-9]+(-[a-z0-9]+)*$`, since a miscased slug would silently disable the self guard); literal `\n` in the PEM become newlines. App JWT: RS256 via `node:crypto`, `iat = now - 60 s`, `exp = now + 540 s`, `iss = appId`. Installation tokens are cached per installation and replaced when `now >= expiresAt - 5 min` on the `IClock`; concurrent callers share one exchange, a failure is not cached. `octokit(id)` builds a `PaginatedOctokit` per call with the cached token; `botLogin()` is `<slug>[bot]` from `slug` or one `GET /app` (single-flight, a failure not cached; an answer without `slug` is a failure, never a `[bot]` login); logins are compared case-insensitively (`isSameLogin`). Tokens, the key and JWTs are never logged or stored; a failed exchange rejects with Octokit's `RequestError` (its authorization header redacted).
- `githubWebhook({ events, id?, filter?, idempotencyKey?, concurrencyKey? })`: `source: 'github'`, id `github:<events joined by ','>`, events `name` or `name.action` (`^[a-z0-9_]+(\.[a-z0-9_]+)?$`, digits for `projects_v2_item`), default concurrency key `<full_name>#<issue|pull_request number>`, else `<full_name>`, else none. The payload is a `GithubEvent { name, action?, delivery, installationId?, payload }`.
- `gh.webhookRoute({ path? })` (`POST /webhooks/github`, `rateLimit: false`): `X-Hub-Signature-256` missing 401; `X-GitHub-Event` not `^[a-z0-9_]+$` or `X-GitHub-Delivery` not 1..255 characters without NUL 400; `readBody()` (413, 415 for a form-encoded hook); HMAC-SHA256 over the raw bytes under every secret (constant time, all checked) else 401; non-JSON or non-object 400. Then per agent its first matching trigger and keys `trigger.idempotencyKey?.(event) ?? delivery` and `trigger.concurrencyKey(event)`, all computed before any dispatch; a throwing `filter` or key function fails that agent only (`onError`, the others continue, answer 500), and `dispatch` refuses a key over 255 characters or with NUL (`assertTriggerKey`) the same way. With a match and a `Bot` sender whose login equals `botLogin()`, nothing is dispatched. ## Sandbox and Coding

`@chamvi/sandbox` holds the contracts and shared rules, three providers implement them, `@chamvi/coding` adds the coding tools. Nothing in these packages throws `FatalToolError`: model input the model can correct is a core `ValidationError`, a workspace or provider failure a core `SandboxError` (`sandbox_error`), both tool errors; option misconfiguration is `InvalidAgentDefinitionError`.

- **Contracts**: `ISandboxProvider { name, create(options), collectGarbage() }`; `IWorkspace { id, info, disposed, exec(argv, { cwd?, timeoutMs?, stdin?, signal? }), readFile(path), writeFile(path, content), dispose() }`; `IExecTransport { exec(argv, { stdin?, stdout, stderr, signal }) -> { exitCode }, alive?(signal), remove() }` (`stdout`/`stderr` are `IOutputSink`s the workspace owns). `WorkspaceCreateOptions { runId, repo?, ref?, image?, env?, limits?, signal? }` (`repo` already normalized). No `git` method: git is `exec(['git', ...])`. Workspace ids are `randomUUID()`, so `chamvi-ws-<id>` is a valid container name, pod name and label value. A provider builds `WorkspaceInfo { runId, provider, repo?, ref?, createdAt, expiresAt }`, calls `prepareWorkspace(workspace, { repo, ref, signal })` and sets `info.commit`; a failed checkout disposes the workspace.
- **Rules** (every provider): exec takes argv only (`readonly string[]`, non-empty, no NUL); the only shell is the coding `bash` tool's `['sh', '-c', command]` inside the workspace. Paths (`resolveWorkspacePath`) are relative to the root or under `/workspace/`, the model always sees `/workspace`; empty, NUL, other absolute paths and escapes are `ValidationError` before any filesystem or exec call. Output is capped per stream at `OUTPUT_MAX_BYTES` 65 536 (`createOutputCollector`: drains past the cap, holds at most the cap, a cut UTF-8 character dropped) with `stdoutTruncated`/`stderrTruncated`. Files are UTF-8 of at most `FILE_MAX_BYTES` 1 MiB; `readFile` decodes strictly (`decodeUtf8File`), a file that is not valid UTF-8 is a `SandboxError`. Exec timeout default `EXEC_TIMEOUT_MS` 300 s, max `EXEC_TIMEOUT_MAX_MS` 1800 s, never past `expiresAt`; `timedOut` is a result. A command that cannot start exits 127.
- **Repositories** (`normalizeRepo`): `owner/name` -> `https://github.com/owner/name.git`, an https URL without credentials, query or fragment, `file:///abs` only with `allowFileRepos`; `allowRepo(url)` narrows; the `ValidationError` never echoes the input. Refs (`assertGitRef`): `^[A-Za-z0-9][A-Za-z0-9._/+-]{0,254}$` without `..`, `//`, `@{`, `/.`, a trailing `/` or `.`, `.lock`. Checkout (`checkoutCommands`, same on every provider, through the workspace's own exec): `git init -q .`, `git remote add origin <url>`, `git -c credential.helper= fetch -q --depth 1 origin <ref or HEAD>`, `git -c advice.detachedHead=false checkout -q FETCH_HEAD`, `git rev-parse HEAD`; repo-less workspaces only `git init`. A failed step is a `SandboxError` with the first 2000 characters of git's stderr.
- **Environment and limits**: containers and pods get only `SANDBOX_ENV` (`HOME=/tmp`, `GIT_TERMINAL_PROMPT=0`, `GIT_CONFIG_NOSYSTEM=1`, `safe.directory=/workspace` via `GIT_CONFIG_COUNT/KEY_0/VALUE_0`, `NPM_CONFIG_UPDATE_NOTIFIER=false`, `CI=true`) plus the configured `env` (`assertSandboxEnv`: keys `^[A-Za-z_][A-Za-z0-9_]*$`, no NUL); local gets the host `PATH`, `HOME`/`TMPDIR` in its folder and the same git settings minus `safe.directory`. `DEFAULT_LIMITS` `cpu '1'`, `memory '2Gi'`, `storage '4Gi'`, `pids 512`, `timeoutMs 1_800_000` (`resolveLimits` merges layers over them, Kubernetes quantities); `/tmp` is a `TMP_SIZE` 512 MiB tmpfs. Labels `SANDBOX_LABELS` (`app.kubernetes.io/managed-by=chamvi`, `app.kubernetes.io/component=sandbox`), `chamvi.dev/run`, `chamvi.dev/workspace`; expiry `chamvi.dev/expires-at` (epoch ms; a Docker label, a k8s annotation). No agent label (names may exceed 63 characters).
- **Remote workspaces** (`createRemoteWorkspace`, Docker and k8s): argv wrapped as `timeout -k 5 <s> ...` (`wrapTimeout`; GNU `timeout` signals its process group) inside `EXEC_SCRIPT` (`sh -c` with a fresh marker `chamvi-exit-<32 hex>:` and the cwd made absolute under `/workspace`): the script enters the cwd (else prints `<marker>cwd` and the exec rejects `SandboxError('cwd /workspace/<p> is no directory in the workspace.')`, as on local), runs the command and prints `<marker><status>` on stderr. The workspace owns the output collectors and cuts the marker out of stderr (`createExitMarkerFilter`, also split across chunks); `EXIT_DRAIN_MS` 2 s after the marker it settles with that exit code and the output so far and detaches the transport, so a background job holding the output (`node server.js & echo started`) never stalls an exec, on Docker (whose daemon drains 2 s too) and k8s (whose exec status waits for every pipe writer). A client-side guard at timeout + `EXEC_GRACE_MS` 15 s (exit 137, `timedOut`, the output so far); `timedOut` also for exit 124/137 once the timeout passed (`isTimeoutExit`). `readFile` is `cat -- <abs>` capped at `FILE_MAX_BYTES + 1`, `writeFile` `sh -c WRITE_FILE_SCRIPT` with the bytes on stdin (`mkdir -p`, then `head -c <bytes>` into `.chamvi-write-<16 hex>` next to the file, `cp -p` first to keep an existing file's mode, then `mv -f` over it, so a concurrent reader or writer never sees a cut file; a symbolic link or a directory that takes no new file is written in place; no stdin EOF needed, so k8s `v4` works). Abort detaches (the transport drops the stream); dispose rejects every in-flight exec with `SandboxError('workspace disposed')`, then `transport.remove()` (retried on a later dispose after a failure). A failed exec asks the optional `transport.alive(signal)` (bounded by `ALIVE_PROBE_TIMEOUT_MS` 5 s; a rejection or no answer reads as alive): `false` (Docker: inspect 404 or `State.Running` false; k8s: read 404, a `deletionTimestamp`, or `podState` failed) marks the workspace gone, so `IWorkspace.disposed` reads true and every call rejects with "workspace <id> is gone ...; call create_workspace for a new one" (local: its directory missing, checked when a cwd or file is missing and before every write).
- **Providers**: `createLocalSandbox({ root?, env?, limits: { timeoutMs }?, clock? })` (`<root>/<id>/{workspace.json,home,tmp,repo}`, `writeFile` through a temporary `.chamvi-write-<hex>` file with the old mode and a `rename`, like the remote script; file paths and the cwd resolved with `realpath` before each call and refused (`ValidationError`) when they leave the root through a symbolic link or pass a dangling one (remote providers need no check: a link resolves inside the container), spawn with `detached: true`, timeout/abort/dispose kill the group with `SIGKILL`, the kill timer cleared on exit, `KILL_GRACE_MS` before closing pipes a leaver holds; a command that exited while a background job holds its pipes settles `KILL_GRACE_MS` after its `exit` with its own code and `timedOut: false`, and its group is remembered at the exit while a member still runs (also with redirected output), dropped once `process.kill(-pgid, 0)` fails (checked every `LINGER_CHECK_MS` 1 s, so a reused group id is not killed) and killed on dispose, matching Docker and k8s; no isolation). `createDockerSandbox({ docker?, image?, network?, pull?, env?, limits?, clock? })`: container `chamvi-ws-<id>`, `Cmd: sleep <lifetime>`, `User 1000:1000`, `ReadonlyRootfs`, `CapDrop ALL`, `no-new-privileges`, `PidsLimit`, `Memory` = `MemorySwap`, `NanoCpus`, `/tmp` tmpfs `rw,exec,nosuid,nodev` (Docker adds `noexec` unless `exec` is given; npm's global bins and corepack live there, like k8s' memory emptyDir), an anonymous `/workspace` volume removed with `{ force: true, v: true }`; `pull` `'missing'` (pull once on a 404), `'always'`, `'never'`; the create's `signal` is passed to the pull (the progress stream destroyed), the container create (a container made anyway removed by name) and the start; `network` default `bridge`, `none` allowed (repo-less only); storage not enforced. `createKubernetesSandbox({ namespace, kubeConfig?, image?, env?, limits?, podLabels?, imagePullPolicy?, startTimeoutMs?, pollMs?, clock?, client? })`: a bare pod (`restartPolicy: Never`, `activeDeadlineSeconds`, `automountServiceAccountToken: false`, `enableServiceLinks: false`, non-root 1000, seccomp `RuntimeDefault`, read-only root, caps dropped, requests = limits incl. `ephemeral-storage`, emptyDir `/workspace` with `sizeLimit`, memory emptyDir `/tmp`), `podLabels` may not name a managed label; `create` polls the pod on the `IClock` every `POLL_MS` up to `START_TIMEOUT_MS` (120 s) and fails fast on `FATAL_WAITING_REASONS`; `IPodClient` wraps `CoreV1Api` and `Exec` (stdin closed only on `v5.channel.k8s.io`); pids via the kubelet's `podPidsLimit`. RBAC: `pods` create/get/list/delete, `pods/exec` get and create. All three run `describeWorkspaceContract`.
- **Garbage collection**: `provider.collectGarbage()` deletes that provider's expired workspaces (local: folders whose `workspace.json` expired; Docker: containers with the managed labels past `expires-at`; k8s: pods past the annotation or in phase `Failed`/`Succeeded`), disposing open ones of the process first. A removal that fails never stops the pass: the rest go on, and one `SandboxError` (`collectionError()`, the count and the first message, every failure in an `AggregateError` cause) is thrown at the end. Docker and k8s workspaces also stop themselves at expiry (`sleep`, `activeDeadlineSeconds`).
- **Manager** (`createWorkspaceManager({ provider, image?, env?, limits?, allowFileRepos?, allowRepo?, maxWorkspacesPerRun?, gcIntervalMs?, clock?, onError? })`): workspaces keyed by `(runId, normalized repo or '')`; `acquire(runId, { repo?, ref?, signal? })` shares one create per key (`reused`), refuses another ref of a held repo and more than `MAX_WORKSPACES_PER_RUN` 3 (pending creates count) with `SandboxError`; `get(runId, id?)` (the run's only live workspace without an id, `ValidationError` for several) disposes expired and gone (`workspace.disposed`) ones and answers "not found" for an id of another run; `acquire` drops an expired or gone workspace and creates anew; `release(runId, id?)`; `attach(engine)` disposes a run's workspaces on `run.updated` with `completed | failed | cancelled` (kept while `waiting` or `interrupted`); `collectGarbage()` disposes its own expired workspaces, then calls the provider's (started by `acquire` at most every `GC_INTERVAL_MS` 10 min, `0` disables); `close({ timeoutMs? })` unsubscribes, aborts the creates in flight (each create gets the caller's signal combined with a per-entry abort) and disposes everything, waiting for both, for every disposal started earlier (a run that settled during `engine.drain()`, an expired or gone workspace; the manager tracks each) and for every create in flight a settled run's release aborted (the provider's abort cleanup, or the dispose of a workspace created anyway; reported as `a workspace of run <id> still being created`) at most `CLOSE_TIMEOUT_MS` 30 s, then reports what is still being disposed to `onError` and resolves (call after `engine.drain()`); `release(runId)` aborts and waits for the run's creates in flight too; afterwards `acquire` rejects. A workspace created while its run was released is disposed. Workspaces live in one process: a run resumed elsewhere gets "not found, call create_workspace again" (re-attach by label is plan 020).
- **Context and module**: `provideSandboxContext(engine, manager)` / `injectSandboxContext(ctx)` (key `sandbox`) in the main entry, so a tools factory builds `manager.tools()` and `codingTools(manager)` per execution. `sandboxModule()` on `@chamvi/sandbox/module` picks the provider (`CHAMVI_SANDBOX_PROVIDER`, else the option, else `local`), builds `.manager` when called, imports the provider package in `setup` by variable specifier (`SANDBOX_PROVIDER_PACKAGES[name]`, structural types: a literal import would make `build:types` need the provider's `dist`, a build cycle since every provider peers on `@chamvi/sandbox`; the providers are in none of sandbox's dependency fields, not even as optional peers or a devDependency, since release-please's graph would close `sandbox <-> provider`: the import resolves from the installed tree (npm and pnpm's default hoisting; under Yarn PnP or pnpm `hoist=false` pass `options.provider`), and the module spec loads sandbox-local through its source alias; `isPackageNotFound` is a local copy), and its hooks attach the manager and provide it (`engineCreated`) and `detach()`/`close()` it after the drain; migrate mode does nothing.
- **Tools**: `manager.tools()` = `create_workspace { repo?, ref? }` -> `{ workspace, root: '/workspace', repo, ref, commit, expiresAt, reused }` and `dispose_workspace { workspace? }`. `codingTools(manager)` (needs only `get`) = `read_file`, `write_file`, `edit_file`, `grep`, `list_files` (both `git --literal-pathspecs`, tracked plus untracked, not ignored), `bash` (`sh -c` with `cwd?`, `timeoutMs?`, returns the `ExecResult`), `git_diff` (`status --short` plus the diff, `staged?`); each takes an optional `workspace` id resolved with `context.run.runId`; camelCase result keys. All are plain `defineTool()` tools, **not effect tools**: a workspace dies with its process while an effect record survives, so a redone step on a fresh workspace would skip a recorded write, and two identical `bash` calls of one step would merge; re-applying is safe (`write_file` idempotent, `edit_file` fails with "oldString not found", `bash` in a disposable sandbox, nothing outside the workspace changes).
- **Coding backend**: `ICodingBackend { code({ workspace, task, budget?, signal? }): Promise<{ status: 'done' | 'stuck', summary, diff }> }`, contract only (own-tools backend: plan 019; Claude Code: plan 014).
- **Security model**: local isolates nothing. Docker and k8s are a code-execution boundary, not a network boundary: on `bridge` a workspace reaches the host gateway, other containers and cloud metadata, on k8s every cluster service, until 011's NetworkPolicy (select `app.kubernetes.io/component=sandbox`, deny all egress but GitHub and npm, deny the chamvi namespace and metadata) or a host firewall. Docker socket access is root on the host (socket proxy or rootless Docker). No credentials in URLs, `credential.helper` reset, no host or chamvi environment, no service account token.
- **Image**: `images/sandbox-node` (`node:24-trixie-slim` + git, ca-certificates, tini; uid 1000; npm cache, prefix and corepack under `/tmp`), `ghcr.io/chamvi/sandbox-node` tags `24` and `24-<short sha>` (the latter only on a push to `master`, so a scheduled or manual rebuild never moves it; Dependabot ignores Node.js majors), `linux/amd64` + `linux/arm64`, built by `.github/workflows/images.yml` (smoke test on PRs touching `images/**`, pushed through `tada5hi/craneship` on `master` and weekly). `DEFAULT_SANDBOX_IMAGE = 'ghcr.io/chamvi/sandbox-node:24'`; pin a digest in production.

## Notifiers

`INotifier.notify(n, opts: NotifyOptions)` (`notify/types.ts`): `NotifyOptions = { idempotencyKey, trigger }`. The engine only sends `approval` notifications (`stuck` and `result` sending is deferred to plans 013/014; both transports render every `kind`). Notifiers throw on failure (the engine's `waiting.notifiedAt`, the `notify:<run>:<approval>` lock and the `tick()` resend are unchanged) and stay idempotent on the key. Option misconfiguration, also when detected at notify time (GitHub: no issue and no `target`, no installation), is `InvalidAgentDefinitionError`; transport failures are a `ChamviError` with code `openclaw_request` or `github_request`. Both bound a send to 30 s on the `IClock` (an `AbortController` armed before the first `await`, its reason the timeout error, cleared in `finally`; an abort rejects with that error itself, whatever the transport wrapped it in), below the 60 s notify lock, and cut `Notification.body` (`cutText`: never ends on a high surrogate, appends `… (cut, <n> more characters)`).

- **`consoleNotifier({ name?, write? })`** (core, `notify/console.ts`): writes `[chamvi] <kind>: <title> (agent, run, key)`, the body and an approval's `resume token: <t> (expires <ISO>)`, one `write` (default `console.log`) per line; never throws.
- **`openclaw({ name?, baseUrl, hooksToken, hooksPath?, agentId?, deliver: { channel, to, accountId? }, approvalUrl?, resumeTool?, timeoutMs?, clock?, fetch? })`** (`@chamvi/notify-openclaw`, global `fetch`, no runtime dependencies): `POST <baseUrl><hooksPath>/agent` (default `/hooks`, trailing slashes dropped, a base path kept; a `hooksToken` that is no valid header value, i.e. control characters, characters above U+00FF or surrounding whitespace, is `InvalidAgentDefinitionError`), `Authorization: Bearer <hooksToken>`, `Idempotency-Key` = the key, or `sha256:<hex>` when it is over 256 characters or not visible ASCII (`transportKey`; OpenClaw silently ignores a longer key), body `{ message, name: 'chamvi', agentId?, deliver: true, channel, to, accountId? }`. The message is deterministic (no clock value or random id; OpenClaw starts a new run for a changed body under the same key): a relay instruction, title, body cut to `MESSAGE_BODY_MAX_LENGTH` 8 000, `Agent`/`Run`, and for an approval `Expires`, `Approve or deny: <approvalUrl({ runId, approvalId, agent })>` (only with `approvalUrl` and an `approvalId`) and the `resume_run` call with the token only with `resumeTool: true` (owner decisions: `resumeTool` default `false`, a non-boolean is `InvalidAgentDefinitionError`; approval links are token-less, `approvalUrl` gets ids only, suggested `https://<app>/ui/approvals?run=<runId>&approval=<approvalId>`, the signed-in owner answers in the UI through `POST /runs/:id/approve` (needs `agent:<agent>:approve`, plus `run:read` or `agent:<agent>:run` for the UI to show the run); so by default the token is nowhere in the request, and without a link the block ends with `NO_TOKEN_HINT` "answer in the chamvi UI (or through POST /runs/:id/approve)", never MCP, since `resume_run` needs the token; OpenClaw's MCP principal needs only `agent:<name>:run`, and `agent:<name>:approve` only alongside `resumeTool`, with which a prompt injection in the body can make the relay agent approve, documented as a warning tied to `resumeTool`). Any 2xx resolves; otherwise `OpenClaw <status>: <text>` (`(retry after <v>)` for `Retry-After`), `OpenClaw request failed: <message> (<cause message>)` (redacted and cut like the response text), `OpenClaw did not answer within <ms>ms.`; the response text has `hooksToken` and `n.resumeToken` (sent with `resumeTool` only, still redacted always) replaced by `[redacted]`, then is cut to 500 characters. Verified OpenClaw facts (2026-10-21): hooks off by default, `channel: 'last'` and partial destinations are 400, bodies over 256 KiB 413, `200 { ok, runId }` means admitted (not delivered), replay entries live in memory for 5 minutes after completion and a restart clears them, so `waiting.notifiedAt` is the primary dedupe. OpenClaw runs an agent turn on the message and treats it as external content.
- **`githubNotifier({ app, name?, mention?, target?, approvalUrl?, timeoutMs?, clock? })`** (`@chamvi/notify-github`, `smob`, peer on `@chamvi/github`, whose `REPO_PATTERN` and `GITHUB_REQUEST_ERROR_CODE` it imports): the target is the issue or pull request of a `source: 'github'` run (`payload.payload.repository.full_name` matching `REPO_PATTERN`, `issue.number ?? pull_request.number` a positive integer), else `target`; the installation is `target.installationId` for a comment on `target` (a repository of another installation), else follows `installationIdOf` (the event's for a `github` run, also on the `target` fallback, else `app.installationId`). Per send: `app.octokit(installationId)` with the signal bound through `hook.before('request')`, page `GET .../issues/{n}/comments` (`since` = `receivedAt - 1 h`, 100 per page) and resolve when a `Bot` comment whose login `isSameLogin(botLogin())` holds `effectMarker(markerKey(key))` (`markerKey`: the key when `^[\w:.-]{1,255}$` without `--`, else `sha256:<hex>`); else `POST` the comment: mention line (`@<login>` per `mention`, `LOGIN_PATTERN`), `### <title>` (whitespace runs collapsed to one space, trimmed), the body cut to `COMMENT_BODY_MAX_LENGTH` 60 000 inside a fence one backtick longer than its longest run (at least three; runs over 31 broken with zero-width spaces, so the fence stays short), so mentions and `#123` inside notify nobody; for approvals `Waiting for approval until <ISO>.` plus `Approve or deny: <approvalUrl({ runId, approvalId, agent })>` (ids only) or the hint "Answer it in the chamvi UI or through POST /runs/:id/approve." (never the token, no option adds it; the comment is public), the run line (`Run <id> of agent <name>.`, id and name as inline code), the marker. - Context and modules: each transport keys its notifiers per name (`openclaw:<name>`, `notify-github:<name>`, memoized per name in `context/helpers.ts`), so two modules of one transport with different names both provide; `provideOpenclawContext(engine, notifier)` / `injectOpenclawContext(ctx, name = 'openclaw')` and `provideGithubNotifierContext(engine, notifier)` / `injectGithubNotifierContext(ctx, name = 'github')` live in the main entries; an unknown name throws naming `openclaw:<name>` / `notify-github:<name>`. `openclawModule()` (`@chamvi/notify-openclaw/module`) and `githubNotifierModule({ app })` (`@chamvi/notify-github/module`) contribute the notifier (approval link from `CHAMVI_PUBLIC_URL`, the app's clock) and provide it in `engineCreated`.

## UI

`@chamvi/ui` is the dashboard: a Vue 3 + vuecs SPA (`app/`, Vite root, built to `dist/app`) and a Node entry (`src/`, tsdown) with `uiRoutes()`. It peers on core (its `InvalidAgentDefinitionError`) and http (`import type` only); `@chamvi/http` never imports it. Every SPA library is a bundled devDependency; the SPA imports core and http types only, never their runtime.

- **Serving** (`src/routes/`): `uiRoutes({ basePath? = '/ui', auth?: { tokens? = true, authup? }, root? })` returns an `HttpRoute[]` holding one route (`GET`, `prefix: true`, `rateLimit: false`, unauthenticated), spread into `createHttpApp({ routes })`. `resolveBuildPath(subpath)` decodes the raw subpath once and refuses a decode failure, NUL, backslash, `%` left after decoding (double encoding), a `.`/`..` or empty segment (one trailing `/` allowed), answering 404 (`{ status, code: 'not_found', message }`). `''`, `index.html` or any unknown path without an extension in its last segment answers the rendered `index.html` (`DOCUMENT_CACHE_CONTROL` `no-cache`); a build file its bytes (`ASSET_CACHE_CONTROL` `public, max-age=31536000, immutable` under `assets/`, else `no-cache`); anything else 404. Options are validated at construction (`basePath` `^(?:\/[a-z0-9._~-]+)+$`, lower case since routup matches case-insensitively; authup URL absolute http(s); non-empty `clientId`; `tokens: false` needs `authup`; non-empty `root`). `defaultRoot()` is the first of `dist/app` beside the built entry or seen from `src/routes` holding an `index.html`.
- **App shell**: `readConfig(document)` (else `DEV_CONFIG`), `createUiRouter(config, guards, history?)` (`createWebHistory(uiBase)`, lazy views, global `beforeEach` guards in order: `stripResumeToken`, then `createAuthGuard`), vuecs with the Tailwind theme and the Lucide preset; the Lucide icons the preset names are bundled through the `virtual:chamvi-icons` Vite module (`addCollection`), since Iconify would fetch them from its API, which the CSP refuses. ## App and CLI

`@chamvi/app` (library, no process concerns) turns `export default createApp({ agents, modules?, models? })` into a running app; `@chamvi/cli` (bin `chamvi`, citty only) adds argv, entry loading, signals and exit codes. Contract: `.agents/plans/011-deploy-kit.md` C1 to C5 while it lives.

- **App**: `createApp()` is synchronous and side-effect free (refuses options that are no object or an `agents` that is no array (no agents at all is refused by `chamvi:agents` at `start`/`runJob` unless `CHAMVI_AGENTS_DIR` is set), a `modules` entry that is no `IModule` object, since orkos would `import()` a string, and a name used twice, a built-in's included) and branded (`APP_BRAND`, `isApp()` matches another installed copy). Each lifecycle (`start({ env?, dev? })`, `runJob({ agent, trigger?, env? })`, `migrate({ env? })`) builds one orkos `Application` over a fresh eldin `Container` with `AppToken.CONTEXT` (`mode` `start`/`job`/`migrate`, `dev`, `env`, the stop `signal`, `report`, `models`, `agents`) registered first; an app runs one lifecycle (`app_in_use` after it, also after `stop()`). orkos graph errors (a dependency the app does not register, a cycle, a version mismatch) become `InvalidAgentDefinitionError` (`toSetupError()`). `stop()` is memoized: it aborts the context signal (`app_stopped`), waits for the lifecycle in flight, tears down; a setup error answered by `app_stopped` is logged, never lost; every teardown error is reported (orkos swallows them, `reportingModule()`) and `stop()` (or a job's teardown) then rejects with `app_stop_failed`. A module whose `setup` throws is never torn down by orkos, so each destroys its own partial state first; one whose `onReady` threw is, so every `teardown` tolerates half-built state.
- **Modules**: built-ins in order `chamvi:config`, `chamvi:store`, `chamvi:static-tokens`, `chamvi:engine`, `chamvi:agents`, `chamvi:scheduler`, `chamvi:http` (`ModuleName`), each replaced in place by a user module of the same name, then the user modules. `setup` contributes to the collection tokens (`HTTP_ROUTES`, `NOTIFIERS`, `AUTHENTICATORS` with an `order`, `LIFECYCLE_HOOKS`); `onReady` consumes (engine: notifiers; http: authenticators, routes), so contributions need no order; a module resolving `ENGINE`, `SCHEDULER` or `SERVER` in `onReady` lists it in `dependencies`. Start steps (`module/start.ts`, internal): the engine and scheduler modules register `engine.start()` and `scheduler.start()` in `onReady`; the app runs them once every `onReady` ran (user modules included): `engine.start()`, `scheduler.start()`, then the http module's serve step (the `started` hooks, i.e. the purge timer, then `serve()` and `ready()`); without the http module the app runs the `started` hooks itself and the `stopping` hooks before the teardown. So a configuration error found in any `onReady` starts nothing and executes no queued run of the shared store. Hooks: `engineCreated` (start and job), `started`, `stopping` (inside `createShutdown`'s scheduler step), `drained` (after the engine drained, before the store closes); a throwing hook is reported, the others run. The static-tokens module contributes `CHAMVI_TOKENS` in `setup` and, in dev without any other authenticator, a random `*` token (id `dev`, logged once) in `onReady`; http lists it as an optional dependency. Optional modules live in the feature packages on a `/module` subpath (`@chamvi/github/module` `githubModule`, `@chamvi/notify-github/module` `githubNotifierModule`, `@chamvi/notify-openclaw/module` `openclawModule`, `@chamvi/sandbox/module` `sandboxModule`, `@chamvi/ui/module` `uiModule`; `@chamvi/app` an optional peer there, `src/module/` the only folder importing it, kept external in `dist/module.mjs` so one `AppToken` set exists per process) and provide their instance in the `engineCreated` hook through the package's context pair; a throwing `engineCreated` hook (e.g. a second provide of one key) is caught by `runHooks` and reported through `context.report()`, the app still starts. `@chamvi/app` keeps only `/authup` (`authupModule`, `oidcModule`: moving them to `@chamvi/http` would make http depend on app, a cycle) and `/testing` (`buildModuleHarness()`/`createModuleHarness()`: the real lifecycle over the given modules, `reportingModule` and `runStartSteps` included, `reported` collecting `context.report()`), and its main entry exports the module contract (`AppToken`, `ModuleName`, `AppContext`, `ILifecycleHook`, env readers, `approvalUrlOf`, the orkos `IModule` and eldin `IContainer` types). No `@chamvi/*` feature package is in any of its dependency fields. nx 23.3 and release-please's node-workspace plugin (17.x, `updatePeerDependencies: true`) both read the package.json graph: nx turns dev and peer dependencies into static edges, release-please takes dependencies, devDependencies, optionalDependencies and peerDependencies, and a cycle aborts the whole release run (`found cycle in dependency graph`, nx exclusions do not reach it). So the graph is acyclic in all four fields, without `nx.implicitDependencies` exclusions: `@chamvi/test-kit` does not depend on `@chamvi/sandbox` (its workspace contract types `IWorkspace` structurally), which would close `sandbox -> app -> ... -> test-kit -> sandbox`, and `@chamvi/sandbox` names no provider package. `packages/app/test/unit/graph.spec.ts` pins it from `release-please-config.json`. Optional modules read `options.env ?? process.env` and check their options when the factory is called (errors name the variable, never echo a value, also for the values `createGithubApp()` and `openclaw()` refuse) and expose their instance synchronously.
- **Config and env** (`readConfig(env, { mode, dev })`, `env/`): empty is unset, integers `/^\d+$/` and every `*_MS` at most `TIMER_MAX_MS` (2^31 - 1, a larger Node timer fires after 1 ms), booleans `true|false|1|0`; every error names the variable and never its value. `DATABASE_URL` builds a `DataSource` (`STORE_ENTITIES`, `STORE_MIGRATIONS`, `connectTimeoutMS` `STORE_CONNECT_TIMEOUT_MS` 10 s, password masked in place in every error), migrated in migrate mode or with `CHAMVI_MIGRATE`; without it a `MemoryStore` (warned outside dev); `purgeExpired()` hourly in start mode. Model strings `'<provider>:<model>'` resolve through an AI SDK provider registry of the installed built-in providers and their env keys (`createModelRegistry()`, overridden by `models`), checked at `start`/`runJob` (missing package or key: `InvalidAgentDefinitionError`) and installed as `globalThis.AI_SDK_DEFAULT_PROVIDER` only when none is set.
- **Agent folders** (plan 025a; `loader/`, `modules/agents/`): `CHAMVI_AGENTS_DIR` (optional, relative to the cwd) and `CHAMVI_AGENTS_POLL_MS` (`DEFAULT_AGENTS_POLL_MS` 5000, 1 to `TIMER_MAX_MS`) in `AppConfig.agents`. Layout `<dir>/<name>/` (folder name = agent name, `.`/`_`-prefixed entries skipped): `agent.{ts,mts,js,mjs}` (default export `defineAgent()`'s result, checked structurally (`name` a string, `definition` an object) so another core copy's agent passes; its `name` must equal the folder name; its `definition` is re-run through `defineAgent()` once the files are merged, and a `toolsContext` entry there can name only a tool of `agent.ts`, since `defineAgent()` checks it before the merge), `instructions.md` (an error next to `instructions` in `agent.ts`; with neither the agent has none, as `AgentDefinition.instructions` is optional and MCP describes it by name), `tools/<tool>.*` (a `Tool` or a `(ctx) => Tool` factory, name `^[A-Za-z0-9_-]{1,64}$`; merged with `agent.ts`'s `tools`, a clash an error, a factory on either side makes the set a factory), `triggers/<file>.*` (a module's `TriggerDefinition`, or a YAML/JSON data form validated with validup containers: exactly one of `{ cron, timezone?, overlap?, payload? }`, `{ http: true }`, `{ webhook: '/path' }`; the trigger keeps its own id, the file name is free), `state/<coll>.*` (a Standard Schema), `approvals.*` (`'user'` per tool, policy functions in module files only; clashes with `agent.ts` keys are errors). Module files load through one scoped locter `FormatRegistry` whose rule reads with one `jiti` (`moduleCache: false`, `fsCache: false`, `createModuleJiti()`): `readModule()` evaluates each loader-read file with `evalModule(source, { forceTranspile: true })`, since jiti hands a `.mjs` (or type-module `.js`) file under `jiti.import()` to Node's native import, whose cache never forgets it; relative `.ts`/`.mts` imports transpile fresh too, and a JavaScript helper (a `.js`/`.mjs`/`.cjs` file the loader does not read itself, `assertNoScriptHelpers`) is a load error; required JSON is dropped from the CommonJS cache after each read. `createPackageAliases()` pins `@chamvi/*`, `ai` and `@ai-sdk/*` (every non-wildcard exported subpath, ESM conditions, closest `node_modules` of `@chamvi/app` first) as jiti aliases, so an agents dir anywhere (a volume outside the app) gets the app's instances; packages load natively. A `node_modules` folder in an agent folder or the agents dir is a load error (a second copy). `test/unit/loader/identity.spec.ts` pins a module-provided context key injected by a folder tool on the built packages (so nx runs the app's tests after its build). `locter` and `jiti` are dependencies of `@chamvi/app` only. `hashAgentFolder` = sha256 hex over every file (dot-entries skipped) by relative POSIX path, `path\0bytes\0`, taken before and after the read (a difference is `changed while loading`). `loadAgent` throws `InvalidAgentDefinitionError` naming files relative to the agents dir; `loadAgents` returns `issues`. `AgentsModule` (depends on config and engine): `setup` refuses an app without code agents and without a dir (`NO_AGENTS_MESSAGE`), else registers `AGENT_ISSUES` and, in start mode, the lifecycle hook `chamvi:agents-watcher` (`started` starts, `stopping` stops); `onReady` (start and job) checks the dir (`NO_DIRECTORY_MESSAGE`) and boots the watcher: every folder loaded and `putAgent(agent, { revision: hash })`, checked by `MODEL_CHECK` (the engine module's `resolveModels().check`, a no-op with a preset default provider), then (start mode only, never a job) every marker with neither a folder nor a code agent removed; all before the start steps. Before `putAgent` a folder agent passes the `check`: `MODEL_CHECK` and every `AGENT_CHECKS` contribution (scheduler: `assertSchedulable`; http: `assertMcpRunTool` unless `mcp: false`; both in start and job mode), and an `InvalidAgentDefinitionError` from `putAgent` itself (an unknown notifier, thrown before any store write) is an issue too, so nothing a later consumer refuses crashes the boot or cancels runs; `createScheduler` and `createRunToolSource` report a folder agent's failure to `onError` instead of throwing. A load is registered only when it read exactly the poll's stable hash (else `unstable`: nothing recorded, the next stable poll decides; the boot retries `BOOT_LOAD_ATTEMPTS` 3 times). Every poll reads the markers once and records an applied agent whose marker another process moved or removed while its folder is unchanged as an issue (logged `agent revision moved`), without re-syncing. The watcher (`createAgentsWatcher`, internal) polls on the `IClock` (`keepAlive: false`): a folder whose hash differs from the last attempted one loads once two consecutive polls see the same hash, a broken folder is tried once per content (an issue `{ agent, message, at }` logged `agent load failed`, the previous agent kept, no marker written), a folder missing on two polls is removed, a missing agents dir removes nothing, a store failure retries on a later poll; a folder named like a code agent is an issue, never loaded or removed (code wins). `AGENT_ISSUES` reaches `createHttpApp({ agentIssues })` and the UI's agents page notice.
- **Stop order** (C5): `createShutdown().shutdown()` (readiness 503, `CHAMVI_READINESS_DELAY_MS`, scheduler stop and `stopping` hooks, closers, `server.close()`, `engine.drain()`, the close timeout), then the engine module's `drained` hooks (sandbox: `detach()` and `manager.close()`), then the store's `dataSource.destroy()`.
- **CLI**: commands `dev`, `build`, `start`, `run-job`, `migrate`; exit codes `0` success, `1` runtime failure or forced exit, `2` usage or configuration (citty's `CLIError`, `cli_usage`, `invalid_agent_definition`; `exitCodeOf()` takes the codes from `@chamvi/app`). The entry is `--entry <path>` (a bare one is exit 2), else `chamvi.entry` (source commands only), else `src/index.ts` or `dist/index.mjs`. Signals (`installSignalHandlers()`): the first SIGTERM/SIGINT stops (exit 0, or 1 when the stop failed); a repeat within `SIGNAL_REPEAT_MS` (1 s) is the same signal (npm forwards SIGINT while the terminal signals the group); a later one exits 1; `CHAMVI_FORCE_EXIT_MS` (90 s, dev 15 s) after the first exits 1, on a kept-alive timer cleared once the stop settled. `run-job` keeps the job's code over the stop's (a failed run stays 1 after a signal) and prints `<agent>: <status> (run <id>)`. `dev` spawns `node --watch [--env-file-if-exists=.env] <cli> start --dev --entry <src>` detached (the env flag only when `.env` exists at start; Linux `node --watch` fails with ENOENT on a missing env file) (one forwarded signal per signal; SIGHUP and the CLI's exit send SIGTERM) with a stdin pipe only it writes and `CHAMVI_DEV_LINK=1`, so `start --dev` ends the whole group (`kill(-ppid)`) once the pipe closes (the CLI died by SIGKILL). `build` drives tsdown (optional peer) into `<out-dir>/index.mjs` with `clean: true`, refusing an out dir that is the project folder or above it, holds the entry, or holds anything but `.mjs`/`.mjs.map` files. `start --dev` (hidden from the usage) loads `.env` with `node:util` `parseEnv` before the entry import.

## Errors

All errors extend `ChamviError` (ebec `BaseError`) with a `code`: `InvalidAgentDefinitionError`, `InvalidResumeTokenError`, `BudgetExceededError` (`BudgetExceeded`), `FatalToolError`, `IncompleteResponseError` (`incomplete_response`), `ContextNotProvidedError` (`context_not_provided`, a tool error in `execute` and effect hooks, a failed run from the tools factory), `RunNotFoundError`, `ArtifactNotFoundError` (`artifact_not_found`), `InvalidRunStateError`, `LeaseLostError`, `TimeoutError` (`Timeout`), `ToolNotAllowedError` (`tool_not_allowed`, only ever a tool error), `AgentNotFoundError` (`agent_not_found`, `dispatch` for an agent the engine does not hold, http 404), `SandboxError` (`sandbox_error`, a workspace or provider failure, only ever a tool error), `ValidationError`; the codes are `ErrorCode` (`errors/constants.ts`); outside core two more codes exist: `github_request` (`@chamvi/github`'s tool errors, never fatal, and `@chamvi/notify-github`'s send failures) and `openclaw_request` (`@chamvi/notify-openclaw`). A failed run stores `{ code, message }` in `run.error`.
