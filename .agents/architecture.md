# Architecture

## Core Concepts

App, Agent, Trigger, Run, Step, State, Tool, Workspace, Notifier, Store. Keep the concept surface at about ten. chamberu never wraps the AI SDK: models (`LanguageModel`), messages (`ModelMessage`) and tool sets (`ToolSet`) are passed through as-is.

`@chamberu/core` (as built in plan 001) holds: agent and trigger definitions, the `RunEngine`, step checkpoints, budgets, effect tools, approvals with signed resume tokens, recovery and drain, agent state, streaming deltas, structured output, run artifacts (attachments and tool files), the `IStore`/`INotifier` interfaces, `MemoryStore`. Everything time-based goes through an injectable `IClock` (`systemClock`; `ControllableClock` in tests). The public surface is `src/index.ts`. `@chamberu/test-kit` exports `describeStoreContract` and `ControllableClock`.

## Engine

`new RunEngine({ store, agents, resumeSecret, ... })` validates at construction (`InvalidAgentDefinitionError`): `resumeSecret` must be non-empty, agent names unique, every `notify` must name a key of `notifiers`. Defaults: `claimTtlMs` 60 s, `maxConcurrentRuns` 4, `owner` `${hostname}-${pid}`, `clock` `systemClock`, `onError` logs to `console.error`. `start()` recovers and begins polling; `dispatch`, `cancel`, `resume`, `tick`, `recover` and `drain` are the operations. `on(type, listener)` is typed per event (`run.updated` carries `run`, `step.appended` carries `step`, `run.delta` carries `delta`) and sees local events only.

## Agents

`defineAgent({...})` takes a typed config object and returns `{ name, definition }` with the budget defaults applied (`maxSteps: 20`, `timeoutMs: 15 min`). Agent names match `^[a-z0-9]+(-[a-z0-9]+)*$`, at most 64 chars, unique per app; trigger ids must be unique per agent (`InvalidAgentDefinitionError` otherwise). `tools` is a plain `ToolSet` or a factory `(ctx: ToolContext) => ToolSet`, called per execution. `assembleTools` builds one `ToolContext { run, state, artifacts }` per execution (shared by the factory and every call) and passes it as the `ToolLoopAgent`'s `toolsContext` (`as never`: a `ToolSet` infers no context type) only to tools whose `contextSchema === toolContextSchema` (`tool/`: `defineTool()`, `defineEffectTool()` and the state tools set it; `validate` returns the value by identity and rejects a non-object, which fails the run, since the AI SDK validates the context outside its tool-error handling). The agent's `toolsContext?: Record<string, unknown>` entries go unchanged (by reference, never cloned or stored) to tools that are not chamberu's (also to one without a `contextSchema`); an entry naming a chamberu tool or no tool is an `InvalidAgentDefinitionError` (`assertToolsContext`, `agent/helpers.ts`: thrown by `defineAgent` for a plain set, a failed run before any model call for a factory), and a third-party tool with a required `contextSchema` and no entry (or a rejected one) fails the run. `toRunError` turns that AI SDK `TypeValidationError` (`context.field === 'tool context'`) into a `ValidationError` naming the tool and the issue paths only, since the SDK's message (and some validators' issue messages) hold the entry's value, which may be a secret; chamberu's own missing-context issue keeps its message. `StepResult.toolsContext` is never stored (steps are built field by field). `artifacts` (`IRunArtifacts`: `put`, `get`, `list`) is scoped to the run (`get` of another run's artifact is `undefined`) and is no effect by itself (wrap `put` in `defineEffectTool` for exactly once). `output` takes an AI SDK `Output` (`Output.object({ schema })`), passed to `ToolLoopAgent` as is. `approvals` maps tool names to `'user'` or a policy function (`'user' | 'allow' | 'deny'`), translated to the AI SDK's `toolApproval`. `notify` names a notifier registered on the engine (checked in the `RunEngine` constructor). `toolPolicy(toolName, { run })` is applied to the merged tool set (state tools included) in `assembleTools`: the allowed names become the `ToolLoopAgent`'s `activeTools`, so a refused tool is never offered to the model, while every tool stays in `tools` so an approved call from an older history (policy tightened before the resume) still executes through `wrapToolsForRun`, which re-checks every call and answers a refused one with a `ToolNotAllowedError` tool error (the run goes on). A model that calls a refused tool anyway gets the AI SDK's `NoSuchToolError` answer (the tool is not in `activeTools`); `refusedCallError()` (`execute/helpers.ts`) records that tool step as `ToolNotAllowedError` (`tool_not_allowed`), only for a tool of the full set whose invalid call carries a `NoSuchToolError`, so a genuinely unknown tool keeps the SDK's error. The policy should depend only on the run snapshot, so the tool set is stable across executions. `requireToolPermission({ withoutInvoker? })` (`permission/`) offers a tool when the invoker holds `tool:<agent>:<tool>` (`hasPermission`: `*` alone grants everything, a `*` segment matches one segment, segment counts must match; `@chamberu/http` delegates to it); runs without an invoker follow `withoutInvoker` (default `'deny'`).

## Triggers and the Envelope

`cron()`, `http()` and `webhook()` build `TriggerDefinition`s (`{ source, id, options, concurrencyKey?, idempotencyKey? }`). `http({ schema? })` is the control-plane trigger (id `http`, so at most one per agent): REST `POST /agents/:name/runs`, the UI and MCP `run_<agent>` start runs through it (envelope `trigger: 'http'`, `source: 'http'` or `'mcp'`). `webhook({ path, schema?, idempotencyKey?, concurrencyKey? })` is a generic webhook (id `webhook:<path>`, many per agent, `path` must start with `/`, envelope `source: 'webhook'`); the key functions are copied onto the definition only when given. `cron()` validates the expression with cron-parser and stores the overlap policy (default `skip`; others `queue-one`, `allow`), enforced by `@chamberu/scheduler` (see [Scheduler](#scheduler)). Firing cron and HTTP triggers is not part of core: `engine.dispatch(envelope)` is the only intake; `@chamberu/scheduler` fires `cron()`, `@chamberu/http` serves `http()` and `webhook()` (see [HTTP](#http)), `@chamberu/github` its `githubWebhook()` triggers (see [GitHub](#github)).

```ts
interface TriggerEnvelope {
    id: string;              // defaults to a UUID
    agent: string;
    trigger: string;         // trigger id, e.g. 'http'
    source: 'cron' | 'http' | 'webhook' | 'github' | 'mcp';
    payload: unknown;
    idempotencyKey?: string;
    concurrencyKey?: string;
    thread?: string;
    invoker?: Invoker;       // { id, kind, name?, permissions }, from an authenticator only
    receivedAt: Date;        // defaults to now
}
```

`dispatch` validates a given invoker (non-empty `id` and `kind`, `permissions` an array of strings, `ValidationError` before any write) and stores a copy of only those fields. It is a snapshot (identity and grants, never a token): a run paused on an approval keeps it, and revoking a grant does not reach a run that holds it. The idempotency scope includes the invoker (see Intake), so a deduplicated dispatch always comes from the invoker of the run it returns. Tool code reads it as `context.run.trigger.invoker` (tools and the factory's `run`), `ctx.run.trigger.invoker` (effect hooks) and `runtimeContext.trigger.invoker` (approval policies).

The envelope (source, trigger, payload) is rendered as a JSON block and becomes the run's first user message: string content, or with attachments `[{ type: 'text', text }, ...one file part per attachment]` whose `data` is the marker `chamberu-artifact:<id>` (`ARTIFACT_URI_PREFIX`, internal). `TriggerEnvelope.attachments?: Artifact[]` holds their metadata; `DispatchEnvelope.attachments?: ArtifactInput[]` takes the bytes.

## Run Lifecycle

Run statuses are exactly `queued | running | waiting | completed | failed | cancelled | interrupted`. Steps are `llm | tool | wait`.

```
dispatch -> queued -> running -> completed | failed | cancelled
running -> waiting (approval) -> queued (resume or timeout answers it) -> running
running -> interrupted (drain) -> queued (recover) -> running
running with an expired claim (crash) -> queued (recover) -> running
```

- **Intake**: `dispatch` first refuses an `idempotencyKey`, `concurrencyKey` or `thread` above `TRIGGER_KEY_MAX_LENGTH` (255, the store's varchar width) or with a NUL (`assertTriggerKey()`, `trigger/key.ts`, `ValidationError`, before any store write); intakes (`@chamberu/http` hooks, `@chamberu/github`) use the same helper. With an `idempotencyKey`, `dispatch` claims `(scope, key)` in the `IIdempotencyStore` (TTL 7 days); the scope is `<agent>:<source>`, and with an invoker `<agent>:<source>:<kind>:<id>` with `kind` and `id` each `encodeURIComponent`-ed (`idempotencyScope()`, `trigger/helpers.ts`), so two invokers sending the same key get a run each and one principal cannot squat another's key; a duplicate returns the existing run id with `deduplicated: true`. A key whose run was never created (createRun failed after the claim) is healed by the next dispatch, which creates the run under the reserved id; `createRun` is insert-if-absent, so concurrent healers create it once.
- **Attachments**: `dispatch` validates each `ArtifactInput` (`mediaType` `type/subtype` without parameters, optional string `filename`, `data` a `Uint8Array`; `ValidationError`) before any store write, then, after the idempotency dedupe returned (a duplicate stores nothing), stores each as an artifact of the run (id `<runId>.<index>` from `attachmentIds()` in `artifact/module.ts`, the index zero-padded to one width per dispatch, at least 4 digits, so `listArtifacts` (createdAt, then id) returns the input order; `size` = byte length, `createdAt` = run createdAt) and creates the run. Tool artifacts (`artifacts.put()`) keep `randomUUID()` ids. `storeArtifact` relies on `putArtifact`'s insert-if-absent: when the id is taken by the same run it returns the stored artifact (another run's: `InvalidRunStateError`), so concurrent healers of one reserved key write to the same ids, the second write is a no-op and `trigger.attachments` always names what the store holds (the first writer's bytes). A crash between storing and `createRun` leaves orphan artifacts (accepted; nothing purges artifacts yet), and a racing healer that sends more attachments than the winner leaves its extra indexes listed on the run.
- **Scheduling** (`engine/queue.ts`): a pass lists `queued` runs FIFO (createdAt, then id) and starts them up to `maxConcurrentRuns`. A keyed run starts only when no other run of the same agent and `concurrencyKey` is `running`, `waiting` or `interrupted`; check, claim and transition happen under a store lock `concurrency:<agent>:<key>` so it holds across replicas.
- **Claims**: `claimRun(id, owner, claimTtlMs)` is a lease, renewed every `claimTtlMs / 3`. The poll runs on the same interval and calls `tick()` (approval expiry) and `recover()`. Every write of a running run is conditional on status and owner; an engine that loses its lease aborts the execution, writes nothing more and reports a `LeaseLostError` to `onError`.
- **Execution** (`engine/execute.ts`): one `ToolLoopAgent.stream()` call per execution (consumed to the end; settling reads the result's `steps`, `finishReason`, `text`, `output` promises), starting from the latest checkpoint. Checkpoints hold the stored messages (artifact markers); the model gets a hydrated copy whose marked file parts carry the bytes from `readArtifact` (a missing one fails the run with `ArtifactNotFoundError`), and the engine saves `[...storedInitial, ...responseMessages]`, so the approval resume path works on stored messages. Each `text-delta`/`reasoning-delta` part is emitted as `run.delta` (`RunDelta { runId, step, kind: 'text' | 'reasoning', text }`, `step` = the checkpoint `stepIndex` the step is saved under); deltas are never stored, local to the executing replica and never emitted once the execution was abandoned. No opt-out: every AI SDK provider streams. A model call that fails mid-stream (an `error` part) still ends its step: the AI SDK finishes it with finish reason `error`, so the engine appends the `llm` step (the partial text) and saves its checkpoint before the run fails with that error (unlike the former `generate()`, which wrote nothing; pinned in `stream.spec.ts`). A step whose provider stream closed without its finish part (the AI SDK then synthesizes finish reason `other` and never executes the step's tool calls) fails the run with `IncompleteResponseError` (`incomplete_response`); the engine tells it apart through `onLanguageModelCallEnd`, which fires only for a received finish, so a provider that reports `other` itself still completes.
- **Structured output**: with `output`, a `completed` run's `output` is the parsed value (else the text); a final answer that fails to parse or validate (`NoOutputGeneratedError` or a schema failure) fails the run with `ValidationError` (`validation_error`, message from the cause, the cause cut to `MAX_ERROR_CAUSE_LENGTH` 500 characters plus an ellipsis, `execute/constants.ts`). Before parsing, a loop end with no answer fails with `IncompleteResponseError` (`incomplete_response`, `incompleteOutput()` in `execute/helpers.ts`): finish reason `length` (cut answer) or `tool-calls` outside a budget stop (a call nothing executed, e.g. a tool without `execute`, named in the message). A plain agent keeps completing with the text in both cases (decided: its text is still usable and the llm step records the finish reason). The "step limit reached by an earlier execution" branch parses the checkpoint's last assistant text through `output.parseCompleteOutput` with the same rules (a `length` checkpoint is incomplete). The `ToolLoopAgent` gets `withoutPartialOutput(output)` (`execute/helpers.ts`): a prototype copy whose `parsePartialOutput` returns `{ partial: text }` without parsing, so the AI SDK neither re-parses the accumulated answer per delta nor holds deltas back (returning `undefined` would publish the whole text at `text-end` only); `parseCompleteOutput` and `responseFormat` stay the agent's. After every step the engine appends the steps and saves a checkpoint (messages plus the step's `finishReason`). A cancel or drain abort lets the step-end writes in flight finish (all tool rows and the checkpoint of a completed step), so a recovery does not redo a step whose tools already ran; an abandon guard then stops a still-running generate from writing after the run settled. Each execution owns an `AbortController` combined into the signal the agent and the tools get (`run.signal`); it aborts on every exit, so a throw while consuming the stream (e.g. a throwing `onError` behind a failing `run.delta` listener) cancels the model stream instead of leaving it open.
- **Budgets** (`engine/budget.ts`): `maxSteps` and `maxTokens` are stop conditions, `timeoutMs` an abort signal per execution (built on the `IClock`). Stopped by a budget while the last step asked for tool calls: `failed` with `BudgetExceeded`; otherwise `completed` (a plain agent), or for an agent with `output` the structured-output rules apply (a `length` finish fails with `incomplete_response`). Timeout: `failed` with `Timeout`.
- **Tool errors** go back to the model as tool-error results; only `FatalToolError` (and infrastructure or store failures) fail the run.
- **Cancel**: aborts a local execution (`cancelled`), or marks a `queued`/`waiting` run cancelled. A run `running` on another replica (or `interrupted`) gets `cancelRequested: true`; the owner sees it in `recover()` on its next poll and aborts with stop `cancel`, and an execution that starts on such a run settles it `cancelled` without a model call. A cancel that races a pause (the abort cannot interrupt the `waiting` write) cancels the run the pause left waiting, without notifying.
- **Drain**: `drain({ timeoutMs })` stops polling and starting runs, waits for in-flight runs (default 30 s), then aborts the rest and marks them `interrupted` with the claim released. `stop()` only stops polling.
- **Recovery**: `recover()` (on `start()` and every poll) claims each `running` or `interrupted` run whose claim expired or was released and requeues it; the next execution continues from the latest checkpoint. A step whose checkpoint never landed runs again.

## Approvals

- A tool call needing approval ends the step; the first unanswered `tool-approval-request` becomes the run's `WaitPoint` (`approvalId`, `toolName`, `input`, `expiresAt`, `tokenId`). Other approval requests from the same step are dropped from the history; the model asks again after the resume (one approval per pause).
- `running -> waiting` releases claim and slot (a keyed run keeps its key blocked). The notifier named by the agent gets one `approval` notification per wait point, carrying a resume token; a successful send records `waiting.notifiedAt`. `tick()` re-sends on every poll while `notifiedAt` is missing (a failed send, or a crash mid-send); a store lock `notify:<run>:<approval>` held for one attempt (at most `claimTtlMs`) keeps replicas from sending concurrently, and the notifier's `idempotencyKey` (`<run>:<approval>`) dedupes a send whose record was lost.
- Resume token: `base64url(JSON { runId, approvalId, tokenId, exp }) + '.' + base64url(HMAC-SHA256(resumeSecret, payload))`, compared in constant time.
- `resume(token, decision)` validates an optional `decision.approver` (an `Invoker`, recorded as `output.approver` on the `wait` step), verifies the token against the current wait point, moves `waiting -> queued` (guarded by `expectStatus`, so only one answer writes), appends the `tool-approval-response` to the checkpoint and a `wait` step, then clears `waiting`. A failure undoes back to `waiting`, so the token stays valid; a crash in between re-pauses on the same wait point.
- `inspectResumeToken(token)` checks a token's signature (constant time) and expiry and returns its claims (`runId`, `approvalId`, `tokenId`) without touching the store (`InvalidResumeTokenError` otherwise), so an intake layer can authorize against the run's agent before `resume()`; `resume()` still checks the token against the current wait point.
- `tick()` also denies approvals past `expiresAt` with reason `approval timed out` (default `approvalTimeoutMs` 24 h). A resumed approval gets one step beyond `maxSteps`, so an approval on the last step is still answered.

## Store Contract

The store is a set of small interfaces combined as `IStore` (`src/store/types.ts`):

| Interface | Holds |
|-----------|-------|
| `IRunStore` | Runs; `updateRun` with `expectStatus`/`expectOwner` guards; `listRuns` ordered by createdAt then id, unbounded without `limit`; `claimRun`/`renewClaim` leases |
| `IStepStore` | Append-only steps per run |
| `ICheckpointStore` | Latest checkpoint per run (highest `stepIndex`; equal index replaces) |
| `IIdempotencyStore` | `claimKey(scope, key, runId, ttl)`: first caller wins |
| `ILockStore` | `acquire`/`release` of keyed leases |
| `IEffectStore` | Recorded effect results by effect key |
| `IStateStore` | Per-agent KV and document collections (`where` = top-level equality) |
| `IArtifactStore` | `putArtifact(artifact, data)` (atomic insert-if-absent, `false` keeps the stored one), `getArtifact` (metadata), `readArtifact` (bytes, a plain `Uint8Array`), `listArtifacts(runId)` (createdAt, then id); bytes copied in and out |

Rules every implementation must keep: a TTL created at T with `ttlMs` is expired at exactly `T + ttlMs`; values are copied in and out (no aliasing); atomic operations are atomic across callers. `MemoryStore` implements it in-process (structured clones, no await between check and write). `describeStoreContract((clock) => store)` from `@chamberu/test-kit` is the shared Vitest suite every store must pass; the factory must use the given `ControllableClock` for expiry. Redis is never required.

`TypeormStore` (`@chamberu/store-typeorm`) is the TypeORM store (PostgreSQL only). Every method goes through the entities' repositories and query builders; the only hand-written SQL is the `jsonb_exists` key check in `docList` (TypeORM has no key-existence operator), containment uses `JsonContains`; `store/helpers.ts` maps entities to `Run`, `Step` and `Checkpoint` (a `RETURNING` row is hydrated through the entity metadata). Every atomic operation is one statement: `insert().orIgnore()` returning `id` (`createRun`, `putArtifact`), `insert().orUpdate()` with the overwrite condition `expires_at <= now` returning a row (`claimKey`, `acquire`), a conditional `update()` (`claimRun`, `renewClaim`, the `updateRun` guards, the latter returning `*`) and `insert().orUpdate()` with the overwrite condition `step_index <=` (`saveCheckpoint`). Time comes from the `IClock` as a parameter, never the database's `now()`. Values are `jsonb` through column transformers (`entities/constants.ts`): the Postgres driver writes `JSON.stringify` and turns `null` into SQL `NULL`, so the transformers hand it a `toJSON` wrapper carrying the sanitized value (NUL and lone surrogates become U+FFFD); `JSON_VALUE_TRANSFORMER` (state, docs, effects, checkpoint messages) keeps `null` as JSON `null`, `OPTIONAL_JSON_TRANSFORMER` (run and step columns) stores it as SQL `NULL`. `trigger.receivedAt`, `trigger.attachments[].createdAt`, `waiting.expiresAt` and `waiting.notifiedAt` are revived as `Date`. Only the latest checkpoint is kept. Artifacts live in `chamberu_artifacts` (`ArtifactEntity`: `id` varchar(128) PK, `run_id` indexed, `agent`, `media_type`, `filename` nullable, `size` int, `data` `bytea` with `select: false`, `created_at` timestamptz; migration `1792368000000-artifacts.ts`); `chamberu_idempotency_keys.scope` is varchar(1024) (migration `1792454400000-idempotency-scope.ts`, a hand-written `ALTER COLUMN ... TYPE`, since TypeORM's generated length change drops and re-adds the column); `getArtifact`/`listArtifacts` never load `data`, `readArtifact` returns a plain `Uint8Array`. `migrateStore(dataSource)` runs the migrations under the advisory lock `chamberu:migrations`; `purgeExpired(now?)` deletes expired idempotency keys and locks (nothing calls it automatically yet). Documented divergences from `MemoryStore`: opaque JSON loses `Date`/`undefined`/`Map` fidelity, `null` in an optional run or step property reads back absent, `putEffect(key, undefined)` reads `{ result: null }`, `docUpsert(..., undefined)` reads `doc: null`, `docList` `where` is `jsonb` containment and orders by `id`, `listRuns` ties use `COLLATE "C"`.

## Idempotency and Side Effects

1. Trigger dedupe at intake via `IIdempotencyStore`.
2. Completed steps are never repeated: execution resumes from the latest checkpoint.
3. Side-effecting tools use `defineEffectTool()`. Per call the wrapper (`wrapToolsForRun`) returns the recorded result for the effect key, else asks `alreadyApplied(effectKey, input, ctx)`, else executes and records the result; both hooks get the `ToolContext` (`ctx.run`, `ctx.state`, `ctx.artifacts`), and a custom `effectKey(input, ctx, options)` also gets the AI SDK call options (`toolCallId`, `messages`, e.g. to key by model step). The default key is `${ctx.run.runId}:${toolName}:${sha256(canonical JSON of input)}`. A throwing execute records nothing; a crash between the effect and the record repeats it unless `alreadyApplied` finds it (`effectMarker(key)` is the hidden marker to embed). Parallel identical calls in one step share one application.

## Agent State

`createAgentState(agent, schema, store)`: KV (`state.get/set`) plus typed collections declared as `state: Record<name, StandardSchemaV1>` in `defineAgent`. `upsert` validates with the collection's Standard Schema, mapped through `@validup/standard-schema` (`ValidationError` with the validup `issues` on failure, nothing stored). With a schema, the model also gets `state_<coll>_list`, `state_<coll>_upsert` and `state_<coll>_remove` tools (`createStateTools(schema)`; chamberu tools reading `context.state`, upsert and remove are effect tools); user tools win on a name clash.

## Scheduler

`@chamberu/scheduler` fires `cron()` triggers; it depends on `hubwire` (croner inside) and is a peer of core.

- `createScheduler({ engine, agents, store, owner?, lockTtlMs?, onError? })` builds one hubwire `defineScheduledComponent` per cron trigger, named `cron:<agent>:<triggerId>`, with `lock: createStoreScheduleLock(store, owner)` (`ILockStore.acquire`, never released) and `lockTtlMs` default `SCHEDULE_LOCK_TTL_MS` (10 min). hubwire's tick key is `${name}:${scheduledAt ISO}`. Duplicate agent names and every hubwire definition error (expression croner rejects, timezone, `lockTtlMs`) throw `InvalidAgentDefinitionError` from `createScheduler`, before `start()`.
- `runOnStart: false` always: a start pass never takes hubwire's lock and would fire on every replica. hubwire skips a locked tick fired `lockTtlMs` or more late; `onSkip` is not wired (N - 1 replicas skip every tick). Lock, overlap and dispatch failures reach `onError(error, { agent, trigger })`.
- `fireCronTrigger({ engine, store, agent, trigger, scheduledAt })` is one tick: overlap check, then `dispatch` with source `cron`, payload `options.payload ?? { scheduledAt: ISO }`, idempotency key `<triggerId>@<scheduledAt ISO>` (the trigger's own `idempotencyKey()` is ignored), `concurrencyKey = trigger.concurrencyKey?.(payload) ?? (overlap === 'allow' ? undefined : trigger.id)`.
- Overlap: active runs are `queued | running | waiting | interrupted` of the agent filtered by `run.trigger.trigger`. `skip` skips while any is active, `queue-one` while one is `queued`, `allow` never. The check-then-dispatch race is made harmless by the default concurrency key (the extra run waits).
- Shutdown order: `await scheduler.stop()` (stop, then `settled()` per component), then `await engine.drain()`.
- `runJob({ engine, store, agent, trigger?, clock?, pollMs?, drainTimeoutMs? })` fires once at `clock.now()`, then always starts the engine and calls `engine.tick()` once (so a skipped tick still recovers leftovers of earlier jobs and times out expired approvals), waits via `run.updated` plus an `engine.getRun` poll (`pollMs`, default 1 s, covers another replica) for `completed | failed | cancelled | waiting`, or for `queued` behind a `waiting` run of the same concurrency key (`queue-one` behind an approval), then `drain({ timeoutMs })` (default 30 s). Exit code 1 for `failed`/`cancelled`, else 0; an overlap skip returns `skipped` after the drain. It starts a full engine over the shared store (every queued run of every agent), so size the drain timeout.

## HTTP

`@chamberu/http` is one routup v6 `App` per chamberu app, a peer of core like the scheduler.

- `createHttpApp({ engine, store, agents, auth, basePath?, trustProxy?, shutdown?, bodyLimit?, stream?, mcp?, cors?, rateLimit?, metrics?, readyTimeoutMs?, clock?, onError?, routes? })`. `store` is needed beside the engine because `RunEngine` exposes neither `listRuns`, `listSteps` nor state. Duplicate agent names, an empty `auth` array and a `stream.maxOpen` that is no positive integer throw `InvalidAgentDefinitionError`. Order: plugins, health, agents (incl. `/schedules`), runs, hooks, extra routes, MCP, a trailing catch-all 404, the error handler. Route modules share one internal `HttpContext` (`app/types.ts`).
- Routes: `POST /agents/:name/runs` (the agent's `http()` trigger, source `http`, 404 without one; body `attachments?: Array<{ mediaType, filename?, data }>`, at most `MAX_ATTACHMENTS` 16 (`runs/constants.ts`), validated by `isArrayOf(<attachment Container>, { max: MAX_ATTACHMENTS })` (length checked before any item, item issues prefixed with their index) with `isMediaType` (core's `isArtifactMediaType`, one rule for both packages), `isString` (1 to 255) and `isBase64` (strict RFC 4648 base64, canonical, decoded to a plain `Uint8Array`, never echoing the input in the issue; the other validators pass `boundReceived(value)`, the value only when its JSON has at most `RECEIVED_MAX_LENGTH` 256 characters) from `request/validators.ts`, unknown item keys dropped, passed to `dispatch`; size bounded by `bodyLimit`), `GET /runs/:id/artifacts` (`{ data: Artifact[] }`), `GET /runs/:id/artifacts/:artifactId` (the bytes; `content-type` the stored media type, `content-length`, `content-disposition: attachment` plus `filename`/RFC 5987 `filename*` when named, `x-content-type-options: nosniff`, `cache-control: private, no-store`; both under the run read rule via `loadReadableRun`, an artifact of another run 404 `artifact_not_found`), `GET /runs` (rapiq URL query via `@rapiq/codec-url` 2.4: `filter[agent]`, `filter[status]`, `page[limit]` default 50 max 100, `page[offset]`, `sort=createdAt` only; only `and`-joined leaf filters; page values must be plain integers, as rapiq reads them with `parseInt`; rapiq coerces `123`, `007`, `true`, `null` even when quoted, so a non-string `filter[agent]` maps back to the registered agent whose name coerces to it, 400 when two do), `GET /runs/:id` (run plus steps), `GET /runs/:id/stream` (SSE), `POST /runs/:id/cancel`, `POST /resume`, `POST /hooks/:agent<path>` (`webhook()` triggers on their own `path`, routed as `/hooks/:agent{/*path}`; `GET /agents` lists the `hook` URL, the `webhook:<path>` id stays internal; source `webhook`, the whole body is the payload, `Idempotency-Key` header else `idempotencyKey(payload)`), `GET /agents`, `GET /schedules` (cron definitions with `nextAt`, not scheduler health), `GET/PATCH /agents/:name/state/kv/:key`, `GET /agents/:name/state/collections/:collection` (top-level `eq` filters as `docList` `where`, a double-quoted value kept as a string because rapiq coerces `42`/`007`/`true`/`null`, `filter[id]` 400 since `id` is the store id, `page[limit]`, a `page[offset]` above 0 is 400; documents as `{ id, ...fields }`, a non-object as `{ id, doc }`), `/mcp`, `GET /healthz`, `GET /readyz` (503 `shutting-down`, `draining` or `store-unreachable` within `readyTimeoutMs`), `GET /metrics`. The token-less `POST /runs/:id/approve` and the spec's `POST /runs/:id/resume` are deferred to plan 010.
- Errors: every route under `basePath` answers `{ status, code, message, issues? }`, built by the error handler (never `toJSON()`, which would send `cause`); `withIssues` runs every issue tree through `boundIssues()` (`request/helpers.ts`), dropping a `received` value over `RECEIVED_MAX_LENGTH` whatever produced it (validators, a trigger schema, a core `ValidationError`), so a 400 never echoes a large body. `@ebec/http` errors keep their status (code lower-cased), validup errors are 400 `validation_error`, core codes map `RUN_NOT_FOUND` and `ARTIFACT_NOT_FOUND` 404, `INVALID_RUN_STATE` 409, `INVALID_RESUME_TOKEN`/`VALIDATION` 400 (`INVALID_AGENT_DEFINITION` at request time means the app lists an agent the engine lacks: 500); anything else is 500 `Internal Server Error` and goes to `onError`. Every 401 gets `WWW-Authenticate: Bearer`. Error responses start from `event.response.headers`, so CORS, `RateLimit-*` and `Retry-After` survive.
- Auth: `Authenticator = (request) => Promise<Principal | undefined>` (`undefined` lets the chain continue, a throw is a 401 remembered while later authenticators run; a resolved principal without a non-empty `id` and `kind` and a `permissions` array of strings is `InvalidAgentDefinitionError`, 500 and `onError`, and ends the chain); the chain runs once per request (memoized on `event.store`). Built-ins: `staticTokens({ tokens: [{ value, id, permissions }] })` (sha256-indexed, `value` at least 16 characters and unique, a non-empty `id` that several tokens may share), `authup()` (`@authup/server-adapter-web` `verifyRequest`; grants only from tokens whose `scope` has `global`), `oidc()` (vouchly; `principal` mapper and a non-empty `audience` per issuer required, as vouchly skips `aud` without one; untrusted issuer or malformed token passes on, unreachable issuer 503, an unknown `kid` 401; a mapper result without a non-empty `id` and `kind` or with `permissions` that are no string array throws `InvalidAgentDefinitionError`, a 500 reported to `onError`). Permissions `agent:<name>:run`, `agent:<name>:approve`, `run:read`, `run:cancel`, `state:read`, `state:write`, `tool:<agent>:<tool>` (read by core's `requireToolPermission()`, never checked by a route), `*`; a `*` segment matches one segment, segment counts must match. Routes match with core's `hasPermission(principal.permissions, wanted)`; http exports only `agentPermission()`, no matcher of its own.
- Reading runs: `run:read` or `agent:<run.agent>:run` (`GET /runs/:id`, the stream, MCP `get_run`); `GET /runs` and `list_runs` without `run:read` must filter to one agent the principal can run (one store query keeps `total` exact). 404 comes before 403 (run ids are random UUIDs).
- Body after authorization: every protected `POST`/`PATCH` authorizes before `readJsonBody` (so an unauthenticated client cannot make the server buffer `bodyLimit`). `POST /resume` authenticates, reads the body, `inspectResumeToken` (400 before any store lookup), loads the run (missing reads as an invalid token), then requires `agent:<agent>:approve` and calls `resume()`. Bodies: JSON media types only (415 at the first non-empty chunk), `bodyLimit` (413; a `content-length` above it is refused unread, which Node discards; a body refused part-way is drained up to `bodyLimit` more bytes, else answered with `connection: close`, because an unread remainder stalls the next request on a keep-alive socket), objects only for REST bodies (validup `Container` with chamberu's own `isString`/`isBoolean`/`isDefined` validators; unknown keys dropped), trigger payloads through the trigger's Standard Schema (`validatePayload`). U+0000 is refused as 400 at the edge (`assertNoNul` on path and query before any route, `isString`, webhook-derived keys, MCP `pattern`s), since Postgres varchar columns refuse it and a lookup would otherwise be a 500.
- Invoker: `toInvoker(principal)` (`auth/helpers.ts`) snapshots `id`, `kind`, `permissions` and a `name` from the claims (`name`, then `preferred_username`; never `email`, which every reader of the run would see; static tokens have none), never the claims themselves. `POST /agents/:name/runs` and MCP `run_<agent>` dispatch with it as `invoker`; `POST /resume` and MCP `resume_run` pass it as `approver`. Webhooks dispatch without one; it never comes from a body.
- `serializeRun()` drops `claim` and the invoker's `permissions` (keeping `id`, `kind`, `name`) from every run that leaves the package (REST, SSE, MCP), `serializeStep()` drops the `permissions` of a `wait` step's `output.approver` (`GET /runs/:id`, SSE): a `run:read` holder must not learn another principal's grants. Wire types `RunView` and `InvokerView` (`runs/types.ts`).
- SSE: subscribe to `engine.on` before the snapshot, send `run.updated` then steps after `Last-Event-ID` (`id` = step index) or `?after=<step index>` (non-negative integer, given once, else 400; a valid `Last-Event-ID` wins, a malformed one reads as absent), then live events (`run.delta` of the run as `event: delta`, `data: { step, kind, text }`, **no `id:`** so `Last-Event-ID` stays a step index; live only, local replica only, never replayed); a store poll every `stream.pollMs` (2 s, on the `IClock`) covers runs executing on another replica and sends `ping` when idle; the stream ends after a settled run. A failing snapshot is an error response (500, 404 for a run gone meanwhile), never an empty 200 stream. Cleanup (unsubscribe, clear the timer, leave `ctx.closers`) runs once: on end, when `write()` returns false, or on `event.request.signal` abort (srvx aborts it on client close). `maxMessageSize` is never passed (an oversize write reads as a disconnect). Bearer auth only: browser `EventSource` cannot send `Authorization`, so browsers use a fetch-based SSE reader that sends `Authorization` and `Last-Event-ID` (or `?after=`).
- Stream cap: one counter per app (`ctx.openStreams`, cap `stream.maxOpen`, default 1000) over open SSE streams and MCP `run_<agent>` waits (`waitSeconds > 0`); `acquireStreamSlot(ctx)` (`app/helpers.ts`) returns an idempotent release or `undefined`. The stream takes its slot after the `?after` check and the shutdown 503, releases it in its one-time cleanup (end, failed write, request abort, failed snapshot or poll, shutdown); over the cap it renders `503 service_unavailable` with `Retry-After: 5` (`STREAM_RETRY_AFTER_SECONDS`) through `renderError`, not reported to `onError`. An MCP wait over the cap answers at once like `waitSeconds: 0` (the run is dispatched, never failed); a wait releases in `finally`.
- MCP: `createMcpHandler()` from `@modelcontextprotocol/server` 2.3 (stateless legacy fallback), `maxRequestBodySize: bodyLimit`; the route reads a `POST` body itself (`readBodyBytes`, same limit and drain) and hands the SDK a buffered `Request`; one `McpServer` per request whose tools depend on the principal, passed with `event.request.signal` in `authInfo.extra` (the SDK's own `ctx.http.req.signal` never aborts on disconnect). Tools: `run_<agent>` per agent with `http()` the principal may run, its definition (payload JSON Schema with `$ref`s re-rooted at `#/properties/payload`, compiled by `fromJsonSchema`) built once per app in `buildRunTools`, which throws `InvalidAgentDefinitionError` for an uncompilable schema or a name above 64 characters (source `mcp`; `waitSeconds` clamped to `maxWaitSeconds` 60; `waitForRun` resolves on `completed | failed | cancelled | waiting` via `run.updated` or a 1 s store poll, or with the stored run on timeout or abort, signal = request signal plus `mcpReq.signal` plus the app's shutdown; never returns the resume token), `get_run`, `list_runs`, `resume_run`. Tool failures are `isError` results; non-HTTP, non-core errors go to `onError`. Idempotency scopes differ per transport and principal (`<agent>:mcp:<kind>:<id>` vs `<agent>:http:<kind>:<id>`, see Intake).
- Extra routes (`routes: HttpRoute[]`, `routes/module.ts`): the extension point other packages plug into (`@chamberu/github`'s webhook route) without routup in their types. `HttpRoute { method, path, rateLimit?: false, handler(request, ctx) }`; the handler gets `{ request, readBody() }` (`request` a body-less copy with URL, method, headers and signal, so the limited path is the only way to the body; `readBody` = content-length check plus `readBodyBytes` with the JSON media type rule: 413, 415, raw bytes, memoized per request) and `HttpRouteContext { engine, agents, clock, onError }`, and returns `{ status, body? }` (`null` sent for a missing body, since routup hangs on `undefined`). Not authenticated by the app's authenticators; thrown errors render like any route's. `buildContext` refuses (`InvalidAgentDefinitionError`) a path without a leading `/`, with `:`, `*` or `{`, a duplicate method and path, a first segment in `RESERVED_ROUTE_SEGMENTS` (`app/constants.ts`) and the metrics path when metrics are on, all compared lower-cased because routup matches paths case-insensitively (`plugins/helpers.ts` lower-cases the request path the same way for the limiter skips, the stream check and `routeLabel()`). `rateLimit: false` routes skip the limiter; `routeLabel()` labels each route by its path. A string `body` is sent as `text/plain`, everything else but `null` as JSON.
- Plugins, in order: `@routup/cors` only when `cors` is given; `@routup/rate-limit` 300 per 60 s keyed by `getRequestIP(event)` (honours the App's `trustProxy`; the library default would trust any `X-Forwarded-For`), skipping `OPTIONS`, `/healthz`, `/readyz` and the metrics path, rendering 429 through the error handler; `@routup/prometheus` at `/metrics` with a fresh `prom-client` `Registry` per app, skipping `GET /runs/:id/stream`, its `path` label the route template from `routeLabel()` (`plugins/helpers.ts`, unknown paths `/_unmatched`; keep it in step with new routes). The limiter runs first so a 429 is not timed. `/healthz`, `/readyz`, `/metrics` and the extra routes (which check their own credentials) are the only routes the app's authenticators do not guard.
- Shutdown: `createShutdown({ engine, scheduler?, server?, readinessDelayMs?, drainTimeoutMs?, closeTimeoutMs?, clock?, onError? })`; `shutdown()` is idempotent and runs: `shuttingDown` (readiness fails), wait `readinessDelayMs` (0), `scheduler.stop()`, the `onShutdown` callbacks (the app registers one that sets `ctx.closed`, ends SSE streams, aborts MCP `run_<agent>` waits (they answer with the stored run) and closes the MCP handler; new streams and MCP requests then answer 503 without `onError`), `server.close()` (not awaited yet), `engine.drain({ timeoutMs: 30 s })`, then at most `closeTimeoutMs` (5 s) for the close before `server.close(true)`. With srvx pass `gracefulShutdown: false` to `serve()`.

## GitHub

`@chamberu/github` connects a GitHub App; it depends on `@octokit/core` with `plugin-paginate-rest` and imports only types from `@chamberu/http` (nx stays acyclic: github -> http -> core).

- `createGithubApp({ appId, privateKey, webhookSecret, installationId?, slug?, baseUrl?, clock?, fetch? })` validates eagerly (`InvalidAgentDefinitionError`: empty `appId`, a key that is no RSA private key, empty secrets, an `installationId` that is no positive integer, a non-empty `baseUrl` that is no absolute https URL without query or hash (`normalizeBaseUrl`; empty is the default API), a `slug` that is not `^[a-z0-9]+(-[a-z0-9]+)*$`, since a miscased slug would silently disable the self guard); literal `\n` in the PEM become newlines. App JWT: RS256 via `node:crypto`, `iat = now - 60 s`, `exp = now + 540 s`, `iss = appId`. Installation tokens are cached per installation and replaced when `now >= expiresAt - 5 min` on the `IClock`; concurrent callers share one exchange, a failure is not cached. `octokit(id)` builds a `PaginatedOctokit` per call with the cached token; `botLogin()` is `<slug>[bot]` from `slug` or one `GET /app` (single-flight, a failure not cached; an answer without `slug` is a failure, never a `[bot]` login); logins are compared case-insensitively (`isSameLogin`). Tokens, the key and JWTs are never logged or stored; a failed exchange rejects with Octokit's `RequestError` (its authorization header redacted).
- `githubWebhook({ events, id?, filter?, idempotencyKey?, concurrencyKey? })`: `source: 'github'`, id `github:<events joined by ','>`, events `name` or `name.action` (`^[a-z0-9_]+(\.[a-z0-9_]+)?$`, digits for `projects_v2_item`), default concurrency key `<full_name>#<issue|pull_request number>`, else `<full_name>`, else none. The payload is a `GithubEvent { name, action?, delivery, installationId?, payload }`.
- `gh.webhookRoute({ path? })` (`POST /webhooks/github`, `rateLimit: false`): `X-Hub-Signature-256` missing 401; `X-GitHub-Event` not `^[a-z0-9_]+$` or `X-GitHub-Delivery` not 1..255 characters without NUL 400; `readBody()` (413, 415 for a form-encoded hook); HMAC-SHA256 over the raw bytes under every secret (constant time, all checked) else 401; non-JSON or non-object 400. Then per agent its first matching trigger and keys `trigger.idempotencyKey?.(event) ?? delivery` and `trigger.concurrencyKey(event)`, all computed before any dispatch; a throwing `filter` or key function fails that agent only (`onError`, the others continue, answer 500), and `dispatch` refuses a key over 255 characters or with NUL (`assertTriggerKey`) the same way. With a match and a `Bot` sender whose login equals `botLogin()`, nothing is dispatched. Dispatch is sequential in agent order without invoker; a failing agent (match, key or dispatch) goes to `onError` and the rest are still dispatched, then the answer is 500 (route result, not thrown, so `onError` sees each failure once); else `202 { delivery, runs: [{ agent, runId, deduplicated }] }` (`runs: []` for ping, unmatched and self-sent events). The signature covers the body only, neither `X-GitHub-Delivery` nor `X-GitHub-Event`: a captured signed body replayed under fresh delivery ids (or under another event name an agent listens on, so `GithubEvent.name` is untrusted too) starts new runs (bounded per key by `concurrencyKey`, not in number), so exposed deployments give the trigger an `idempotencyKey` from body fields only and a `filter` that checks the body matches the event name.
- Tools act as `installationIdOf(ctx)`: the event's `installationId` for `source: 'github'`, else the app's `installationId`, else `FatalToolError`. Every installation request carries the run's `signal` (an Octokit `hook.before('request')` in `withOctokit`), so cancel, drain and the run timeout abort a stalled GitHub call. App-authenticated requests (the shared, single-flight token exchange and `GET /app`) carry no run's signal; `tokens.app()` wraps each in an abort after `APP_REQUEST_TIMEOUT_MS` (30 s) on the `IClock` (setting `options.request.signal` in place, since before-after-hook binds the same options object for every hook), so a stalled exchange rejects all waiters and is not cached. Repositories match `REPO_PATTERN` (GitHub's `[A-Za-z0-9_.-]`, each segment with a non-dot character, so `.`/`..` never fold the URL into another API path; `parseRepo` builds its regex from it). Inputs use `jsonSchema` with `additionalProperties: false` and are re-checked in `execute` (`ValidationError` tool errors); every GitHub failure goes through `toolError()` (`GitHub <status>: <message>`, a `ChamberuError` with code `github_request`, never the request). Read: `github_get_issue`, `github_search_issues` (`advanced_search: true`, at most 20), `github_list_labels` (paginated, 100 per page), `github_get_pull_request`, `github_get_file` (65 536 characters, directory listing), `github_get_latest_release` (`{ none: true }` on 404). Write (effect tools): `github_add_labels` (default key), `github_create_comment` (key `<runId>:github_create_comment:<owner>/<repo>#<n>:<stepOf(options)>` with owner and repo lower-cased, body plus `effectMarker(key)`; `alreadyApplied` pages the issue's comments `since = trigger.receivedAt - 1 h` and returns `{ id, url }` of the App bot's comment holding the marker), `github_close_issue` (`alreadyApplied` when `GET` shows it closed; meant for `approvals: { github_close_issue: 'user' }`). `stepOf` counts the assistant messages before the one carrying a tool-call with `options.toolCallId` that has no `tool-result` in the tool messages after it (the approval path; position-aware, so a provider reusing call ids across steps never points at an earlier step), else all of them; `flow.spec.ts` pins the AI SDK approval path (a resumed comment keeps its step), so one comment per issue per model step and a recovery that regenerates the text still finds the marker.
- Deferred: a repository-scoped token for sandboxes (plans 008/014), a `repos` restriction on the tools.

## Errors

All errors extend `ChamberuError` (ebec `BaseError`) with a `code`: `InvalidAgentDefinitionError`, `InvalidResumeTokenError`, `BudgetExceededError` (`BudgetExceeded`), `FatalToolError`, `IncompleteResponseError` (`incomplete_response`), `RunNotFoundError`, `ArtifactNotFoundError` (`artifact_not_found`), `InvalidRunStateError`, `LeaseLostError`, `TimeoutError` (`Timeout`), `ToolNotAllowedError` (`tool_not_allowed`, only ever a tool error), `ValidationError`; the codes are `ErrorCode` (`errors/constants.ts`); outside core only `@chamberu/github`'s tool errors carry another code (`github_request`, never fatal). A failed run stores `{ code, message }` in `run.error`.
